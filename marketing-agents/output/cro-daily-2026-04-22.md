### P0 (new critical) — Dashboard `WebApplication` JSON-LD advertises features that don't ship

`dashboard/layout.tsx` (currently untracked in `git status`) adds a `WebApplication` JSON-LD block identical in pattern to `compare/layout.tsx`. The declared `featureList` is:

```json
"featureList": [
  "Multi-source event search across Ticketmaster and SeatGeek",
  "Filter by city, keyword, and date range",
  "One-click add to watchlist with target price",
  "Price-drop email alerts when tickets hit your target",
  "Buy / wait / hold recommendations powered by price history"
]
```

Three of these five claims are **false or partially-shipped as of today:**

1. **"One-click add to watchlist with target price"** — The watchlist add UI (`EventCard.tsx:159–170`) is a button with emoji `👁️` and zero target-price field. No inline prompt, no modal, no secondary flow. The user adds an event and then has to navigate to `/watchlist`, find the item, and edit target price — which is also not supported by the UI (watchlist page at `watchlist/page.tsx:221–225` displays `target_price` read-only, does not let the user set or edit it).
2. **"Price-drop email alerts when tickets hit your target"** — Emails fire from the cron (`index.js`, `checkPricesCron`), but since target price is never settable from the UI, this alert channel is functionally unreachable for 100% of users.
3. **"Buy / wait / hold recommendations powered by price history"** — This surface lives on the auth-gated Event Detail page (`event/[id]/page.tsx`), not on the dashboard. Googlebot crawling `/dashboard` JSON-LD will see a promise that the dashboard *itself* delivers recommendations; that promise doesn't match the dashboard experience.

This is the **second structured-data / reality mismatch** identified in 48 hours, the first being yesterday's `compare/layout.tsx`. The pattern is now established: SEO agent (or a human supporting SEO) is shipping `WebApplication` JSON-LD nodes that describe *aspirational* product functionality rather than *current* product functionality. Googlebot's rich-result systems treat this as a content-parity violation.

**Fix options:**

**Option A (15 min):** Remove the three unsupported claims from `featureList`. Leave the two claims that are honest today:

```json
"featureList": [
  "Multi-source event search across Ticketmaster and SeatGeek",
  "Filter by city, keyword, and date range"
]
```

**Option B (concurrent with product fixes):** Keep the claims, but ship the features they describe. This means (a) inline target-price capture on watchlist add (P0 — Day 4), (b) target-price edit in `/watchlist` UI, and (c) moving or linking Buy/Wait/Hold surface to the dashboard result cards. Effort: ~6–10 hrs cumulative, but matches yesterday's Option B recommendation for compare and makes the JSON-LD honest across both surfaces.

**Option C (30 min):** Make the claims conditional. Use schema like `"applicationSubCategory": "Search"` for dashboard and `"applicationSubCategory": "PriceComparison"` for compare, and scope each page's `featureList` to features on *that* page. Right now both pages claim a near-identical feature bundle, which Google can legitimately treat as duplicated-intent content.

**Recommendation:** Ship Option A **today** — 15 minutes, stops the SEO bleed. Ship Option B in parallel over the next sprint. Option C is a nice-to-have for structured-data hygiene but is not time-critical.

**Effort:** 15 min (A) / 6–10 hrs (B, bundled with product fixes) / 30 min (C). **Impact:** Option A stops compounding SEO damage. Option B restores product-promise parity across both gated and ungated surfaces and unblocks the entire price-alert feature that was the original product premise.

### P0 — Dashboard default city is still "Orlando"

`dashboard/page.tsx:27` — `useState('Orlando')`. Same pattern flagged on compare yesterday (`compare/page.tsx:74`). Same consequences: NYC/LA/Chicago traffic sees Orlando pre-filled, must type over it or bounce. For a *search* page where the input box is the primary action, a pre-filled wrong default is a worse UX than a blank field with a placeholder.

The placeholder already reads `"e.g., Orlando, Miami"` (line 93) — the affordance is already there to teach the pattern without polluting the value.

**Fix (identical pattern to yesterday's compare fix):**

```tsx
const [city, setCity] = useState('');

useEffect(() => {
  const cached = localStorage.getItem('ticketscan:lastCity');
  if (cached) setCity(cached);
}, []);

useEffect(() => {
  if (searched && city) localStorage.setItem('ticketscan:lastCity', city);
}, [searched, city]);
```

Bonus: a single shared `useRememberedCity()` hook covering dashboard + compare + venue pages, so a user who searches "New York" on any surface gets New York pre-filled on every subsequent surface.

**Effort:** 15 min (blank default, per page) / 1 hr (shared hook + three call sites). **Impact:** Same estimate as compare: +8–15% search completion on non-Orlando first-time traffic. Low risk.

### P0 — Dashboard search is not URL-addressable

`dashboard/page.tsx:25–33`. All four inputs (`city`, `keyword`, `startDate`, `endDate`) are component state. Nothing is reflected in the URL. A user who searches "Taylor Swift, Los Angeles, July 2026" and finds something useful **cannot share that URL**. Back button drops them on a blank dashboard. Paid ads from Agent 5 cannot deep-link to a pre-filtered result. SEO from Agent 4 cannot target city-keyword combinations as landing targets.

This is one of the largest latent organic growth leaks in the product — URL-driven search is table stakes for the "search" surface of a comparison site. Kayak, Expedia, Google Flights, SeatGeek, StubHub — all share search URLs. We don't.

**Fix (45 min — 1 hr):**

1. On mount, hydrate state from `useSearchParams()`:

```tsx
const searchParams = useSearchParams();
const [city, setCity] = useState(searchParams.get('city') ?? '');
const [keyword, setKeyword] = useState(searchParams.get('q') ?? '');
const [startDate, setStartDate] = useState(searchParams.get('from') ?? '');
const [endDate, setEndDate] = useState(searchParams.get('to') ?? '');
```

2. If any query param is present, auto-execute the search on mount:

```tsx
useEffect(() => {
  if (city || keyword) handleSearch(new Event('submit') as unknown as React.FormEvent);
}, []); // intentionally empty — fire once on mount if params exist
```

3. On submit, update URL with `router.replace()` so the back button doesn't accumulate stale entries:

```tsx
const params = new URLSearchParams();
if (city) params.set('city', city);
if (keyword) params.set('q', keyword);
if (startDate) params.set('from', startDate);
if (endDate) params.set('to', endDate);
router.replace(`/dashboard?${params.toString()}`, { scroll: false });
```

**Effort:** 45 min – 1 hr. **Impact:** Compounds with Agent 4's (SEO) programmatic expansion strategy and Agent 5's (Ads) deep-link ad URLs. Every ad pointed at `/dashboard?city=Miami&q=Heat` becomes a pre-executed search, not a blank page. Every shareable search URL is latent organic traffic. Estimated +15–25% secondary traffic lift from shareable search over 90 days (high-variance estimate — real impact needs analytics).

### P1 — Form inputs are missing autoComplete and mobile keyboard hints

`dashboard/page.tsx:82–134`. The four inputs (city, keyword, start date, end date) are correctly typed (`type="text"`, `type="date"`) but missing:

- `autoComplete="address-level2"` on the city field. This is the standard token for city in `<input>` autofill — browsers pre-suggest the user's city from their profile or prior forms.
- `inputMode="text"` or `autoCapitalize="words"` on keyword. Optional, but on mobile it puts the right keyboard up faster.
- `autoComplete="off"` is **not** set on keyword, so Safari/Chrome may try to autofill with prior form values that aren't events — unrelated to the intended use.

**Fix:**

```tsx
<input
  id="city"
  type="text"
  autoComplete="address-level2"
  autoCapitalize="words"
  value={city}
  onChange={(e) => setCity(e.target.value)}
  ...
/>
<input
  id="keyword"
  type="text"
  autoComplete="off"
  autoCapitalize="words"
  value={keyword}
  onChange={(e) => setKeyword(e.target.value)}
  ...
/>
```

**Effort:** 5 min. **Impact:** Mobile autofill for city is the main win — saves ~1–2 seconds per search on mobile. Secondary accuracy improvements on prior-value contamination.

### P1 — No autofocus, no result-scroll, no loading skeletons

`dashboard/page.tsx`. Three small UX misses that compound:

1. **No autofocus on mount.** A user landing on `/dashboard` sees the search form but must click into the city field manually. Default focus on city (or keyword if city has a cached value) is standard for search-first surfaces.
2. **No scroll to results after search.** If the form is scrolled past on mobile (tall blog-tip section above), the post-search result grid renders but the user is still looking at the form. `resultsRef.current?.scrollIntoView({ behavior: 'smooth', block: 'start' })` on search completion.
3. **No loading skeleton for cards.** The loading state is a disabled button that reads "Searching..." — good, but the result area below stays empty. A 6–9 card skeleton grid during loading reinforces "results are coming" and reduces perceived wait time.

**Fix:**

```tsx
// 1. Autofocus
const cityInputRef = useRef<HTMLInputElement>(null);
useEffect(() => {
  if (!city) cityInputRef.current?.focus();
}, []);

// 2. Scroll to results
const resultsRef = useRef<HTMLDivElement>(null);
// In handleSearch, after setEvents:
setTimeout(() => resultsRef.current?.scrollIntoView({ behavior: 'smooth', block: 'start' }), 100);

// 3. Loading skeleton (simple version)
{loading && (
  <div className="grid md:grid-cols-2 lg:grid-cols-3 gap-6 animate-pulse">
    {[...Array(6)].map((_, i) => (
      <div key={i} className="bg-white rounded-xl shadow-md h-72">
        <div className="h-48 bg-gray-200" />
        <div className="p-5 space-y-2">
          <div className="h-4 bg-gray-200 w-1/4 rounded" />
          <div className="h-5 bg-gray-200 w-3/4 rounded" />
          <div className="h-4 bg-gray-200 w-1/2 rounded" />
        </div>
      </div>
    ))}
  </div>
)}
```

**Effort:** 30 min total. **Impact:** Small per-session lift. Perceived-speed wins are well-documented in search UX research — users who perceive a faster response search more often. Estimate: +5–10% search volume per session.

## Form Rotation: Newsletter Popup

**Finding:** **There is no newsletter popup on the site.** A grep across `web/src` for `popup`, `modal`, `exit-intent` returns exactly two hits: `EventCard.tsx`'s sign-up prompt overlay (which is a modal but not a newsletter popup), and `page.tsx` (homepage — references "popular" keyword, no popup). No dedicated popup component exists.

This means today's form rotation is not an *audit* but a *recommendation*. Given the number of competing P0s, shipping a popup should not jump the backlog — but the specification is worth capturing now so it's ready to pick up when the bottom half of the P0 stack clears.

### Newsletter Popup — Recommended Spec

**Trigger logic:**
- Exit-intent on desktop (`mouseleave` event toward top edge of viewport).
- Scroll-depth on mobile (fires once when user scrolls past 60% of viewport).
- Time-on-site fallback: 45 seconds idle with no conversion action.
- Hard limits: show once per session, once per 30 days per visitor (localStorage-keyed), never to logged-in users, never if user already subscribed (localStorage flag set by NewsletterSignup on success).

**Positioning:**
- Desktop: centered modal over semi-transparent backdrop.
- Mobile: bottom-sheet slide-up (not a full-screen modal — Google penalizes intrusive interstitials on mobile).

**Content:**

```
[headline]   Don't miss your next ticket deal.
[subhead]    We'll email you when prices drop on events you follow.
[form]       [email input] [Get Deals →]
[fine print] No spam. Unsubscribe any time.
```

**Variants to A/B (once analytics lands):**

| Variant | Headline | CTA |
|---|---|---|
| A (control) | Don't miss your next ticket deal. | Get Deals |
| B (outcome) | Get $50 off your next ticket on average. | Claim My Alerts |
| C (scarcity) | 94% of events drop in price before the show — we'll tell you when. | Start Tracking Free |

**Form fields:** Single email field. Never more. Submit attaches `source="popup-{variant}"` to the `/api/newsletter/subscribe` call, so Agent 2 (Email) can cohort the drip by acquisition surface.

**Tracking (when analytics lands):** `popup_shown`, `popup_dismissed` (with dwell time + scroll position), `popup_submit`, `popup_success`. Field-level error tracking on email typos.

**Anti-patterns to avoid:**
- Do not show on the register page or login page.
- Do not show within 5 seconds of page load.
- Do not block Escape key (accessibility).
- Do not re-show on back-button navigation within the same session.

**Effort estimate (when picked up):** 4–6 hrs — includes popup component, trigger logic, variant plumbing, localStorage gating, and shared `NewsletterSignup` integration.

**Impact estimate:** Industry median exit-intent popup capture rate is 2–4% of exits. Applied to anonymous, non-converting traffic, that's +150–400 subscribers/month conservatively once traffic is meaningful. Real impact compounds *after* the newsletter → drip bridge (P0, Day 3) is wired — popups without drip are the same dead-letter queue as every other capture surface today.

**Prerequisite ordering:**
1. Wire newsletter → drip bridge first (makes every new capture live).
2. Ship Analytics wiring (enables popup A/B measurement).
3. Ship popup component last — it captures into a working pipeline.

Ship order reverse of that = building a sprinkler in a desert.
