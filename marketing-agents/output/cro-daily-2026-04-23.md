### P0 (new critical) — Event Detail has no `generateMetadata`. Zero shareability, zero SEO.

Grep confirms: no `export const metadata` and no `generateMetadata` function anywhere in `event/[id]/page.tsx`. No `<title>`, no OG image, no Twitter card. Every shared event URL produces a naked `/event/123`-in-text preview on iMessage, Slack, Discord, Twitter, and Facebook. Google has nothing to index and no signal that this is a page about a specific event.

This is doubly painful because the page is a `'use client'` component (line 1) — a standard `export const metadata` won't work. The fix is a server-component shell that wraps the client page, or a `generateMetadata` in a sibling server file. The canonical Next 16 App Router pattern is:

1. Rename current file to `EventDetailClient.tsx`.
2. Create `event/[id]/page.tsx` as a server component that fetches minimal event metadata (name, date, venue, city) and exports `generateMetadata`.
3. Server component renders `<EventDetailClient />` passing props.

```tsx
// event/[id]/page.tsx (new server component)
import type { Metadata } from 'next';
import EventDetailClient from './EventDetailClient';
import { getEventMetadata } from '@/lib/api-server';

export async function generateMetadata(
  { params }: { params: Promise<{ id: string }> }
): Promise<Metadata> {
  const { id } = await params;
  const event = await getEventMetadata(id); // lightweight GET /api/events/:id/meta
  if (!event) return { title: 'Event Details — TicketScan' };

  const title = `${event.name} Tickets — Price Tracker & Alerts | TicketScan`;
  const description = `Track ${event.name} ticket prices at ${event.venue}, ${event.city} on ${event.dateFormatted}. Get alerts when prices drop below your target. Compare Ticketmaster and SeatGeek.`;

  return {
    title,
    description,
    openGraph: {
      title,
      description,
      type: 'website',
      images: event.imageUrl ? [{ url: event.imageUrl }] : [],
    },
    twitter: { card: 'summary_large_image', title, description },
    alternates: { canonical: `/event/${id}` },
  };
}

export default function Page({ params }: { params: Promise<{ id: string }> }) {
  return <EventDetailClient />;
}
```

Prerequisites:
- Backend needs a lightweight `/api/events/:id/meta` endpoint (or the existing recommendation endpoint must return event name, venue, city, date, image in the same payload — cheaper). ~30 min backend.
- Client component needs to accept the metadata as a prop to avoid double-fetching on first render.

**Effort:** 1.5–2 hrs (frontend refactor + backend meta endpoint). **Impact:** Every shared event URL becomes a rich preview. Every Googlebot crawl produces a real indexable title/description. Organic long-tail for event queries ("when do Taylor Swift Miami ticket prices drop") lands on this page instead of 404ing off the static surface. Estimate: +3–6× organic impression surface for event-detail URLs over 60 days, assuming the pages are in `sitemap.xml` (separate check required — see note to SEO below).

**Note for SEO Agent (Agent 4):** Confirm whether `/event/*` is in the sitemap. If it is, this is a structured-data vacuum — Google is crawling URLs with no title/description. If it's not in the sitemap, this P0 is still valid (social shares, direct traffic, paid-campaign deep links all benefit from metadata) but less SEO-urgent.

## Form Rotation: Watchlist Add Modal

**Finding:** **There is no watchlist-add modal.** The current watchlist-add UX is:
- `EventCard.tsx:159–170` — an unlabeled emoji button.
- Logged-in users who click it trigger a silent `api.addToWatchlist()` call with `eventId, eventName, eventDate, venue, city`. No target-price. No priority. No notes. No seat preference. No price-alert threshold. Toast-level feedback is a single `✓` change on the button.
- Anonymous users see the `showSignUpPrompt` overlay (lines 80–104), which is a sign-up modal, not a watchlist-add modal.

Because no real modal exists, today's "form rotation audit" is, like yesterday's popup audit, a **design spec** rather than a review.

### Watchlist Add Modal — Recommended Spec

**Trigger:** Click on the "Track this event" / "+ Track" button on `EventCard` or on `event/[id]`. For anonymous: show the existing `showSignUpPrompt` (no change). For logged-in: show the *new* watchlist-add modal instead of the current silent POST.

**Positioning:**
- Desktop: centered modal, ~480px wide, semi-transparent backdrop.
- Mobile: bottom-sheet slide-up.

**Fields:**

1. **Event confirmation** (read-only) — event name, date, venue. Confirms to the user they're tracking the right thing.
2. **Target price** (number input, pre-filled with `currentMinPrice × 0.9` rounded to nearest $5). Helper text: "We'll email you the moment prices hit this." This is the P0-Day-5 target-price UI finally getting its surface.
3. **Alert frequency** (radio group, default "First drop only"): "First drop only" / "Every drop below target" / "Weekly summary." Avoids spam-rage from volatile events.
4. **Optional tier preference** (dropdown, default "Any section"): "Any section" / "Upper bowl" / "Lower bowl" / "Floor" — populated from the tier-estimate data if the venue has it.
5. Nothing else. No priority, no tags, no notes. Every field beyond these four reduces completion rate.

**CTA copy:**
- Primary: "Start Tracking · Set Alert at $X" (dynamic with target-price value)
- Secondary: "Track Without Alerts" — adds to watchlist with no target-price, no alert rows. For users who just want a bookmark.
- Tertiary: "Cancel"

**Success state:** Modal dismisses with a toast: "✓ Tracking — we'll email you when prices drop below $X." Include an "Undo" action in the toast (5-sec timer) — critical for misclick recovery on emoji-only triggers.

**Tracking (when analytics lands):** `watchlist_add_open`, `watchlist_add_submit` (with target-price filled vs. empty as a dimension), `watchlist_add_cancel`, `watchlist_undo`, field-level blur events on target-price.

**Anti-patterns to avoid:**
- Do not require target-price to submit. Many users want a bookmark, not an alert. Treat target-price as the *primary* value path but not a gate.
- Do not preselect a target-price that equals the current price (defeats the point). `currentMinPrice × 0.9` is a meaningful default; a user who wants more aggressive can type over it.
- Do not render a modal on `EventCard` grids larger than 10 cards without debouncing — clicking track on multiple events in quick succession should not produce modal-stacking.

**Integration hooks:**
- Backend: `POST /api/watchlist` already accepts `target_price`. Verify (`index.js` watchlist route) — if it silently drops the field, that's a 10-min backend fix.
- Target-price → `price_alerts` cron: confirm the cron's trigger condition reads `target_price` from `watchlist` (it does per `CLAUDE.md` summary — good).
- Alert-frequency: new column `watchlist.alert_frequency` (default `'first_drop'`) + cron respects it. ~20 min migration.

**Effort estimate:** 4–6 hrs cumulative — includes modal component, form validation, shared state with `EventCard` and `event/[id]`, backend column additions, cron frequency-respect logic, undo toast, shared hook extraction (see note at bottom).

**Impact estimate:** Today ~100% of watchlist adds enter with `target_price = NULL` → alert-firing rate is 0% on unalerted rows. A modal that captures target-price even 50% of the time (conservative — half of users will pre-fill, half will "Track Without Alerts") means the price-alert channel goes from dead-letter to live for the first time since launch. This is the single biggest latent-conversion unlock on the product.

This spec is **the feature Day-5 has been waiting for.** It's not just a UI polish; it's the point where the product's entire thesis ("we tell you when to buy") starts actually firing alerts.

**Prerequisite ordering:**
1. Ship the target-price column capture + cron respect (~1.5 hrs backend).
2. Ship the modal (~3 hrs frontend).
3. Wire into both `EventCard` and `event/[id]` (see P0 #5 above for the event-detail variant). ~1 hr.

Do not ship the modal without the backend. Do not ship the backend without the cron respecting it. Sequencing matters here more than on most of today's backlog.
