### The premise of a venue page

Venue pages are the product's **largest cold-traffic surface from SEO** — 24 static pages, generated server-side, correctly indexed with `generateMetadata`, and each rendering a slice of upcoming events at the venue. They are the "front door" for users who Google "Madison Square Garden tickets" or "Chase Center events." These users arrive with **real buying intent but zero product awareness.** They are the single most addressable cold-signup cohort on the site.

This page has **three positives** worth naming first (the pattern below is rare — most pages have one or none):

1. **It correctly implements `generateMetadata`** (lines 26–53) with title, description, OG, and Twitter card. Contrast: `/event/[id]` has none (Day 8).
2. **It's a server component** — correctly indexable, no client-hydration dance.
3. **Its JSON-LD is truthful** (lines 99–126) — `StadiumOrArena` / `PerformingArtsTheater` + `BreadcrumbList`. No aspirational claims about features that don't exist. Contrast: `/dashboard` and `/compare` still advertise features that aren't wired (Day 3/2).

These positives matter because they mean this page is *already getting cold traffic*. It is already being indexed. It is already being clicked from Google. The conversion machinery on the page is what's broken — not the acquisition surface.

And the conversion machinery is **barely there**:

- Anonymous visitor (the only kind that arrives from SEO) sees a venue headline, a capacity number, a list of upcoming events, a seating-tier table with abstract multipliers, and three CTAs — every one of which dumps them onto `/register` with no event context.
- There is no email-capture fallback anywhere on the page for users not ready to sign up.
- There is no social proof.
- There is no price hook in the hero.
- There is no way for a logged-in user to track an event from this page without loading `/event/[id]` first — and then `/event/[id]` is auth-walled and has no purchase CTA (see yesterday's audit).

### P0 (new critical) — "Track Price" CTA on every event links to `/register`, not `/event/[id]`. Event context is thrown away.

`venues/[slug]/page.tsx:213–218`:

```tsx
<Link
  href="/register"
  className="bg-brand hover:bg-brand-dark text-white px-4 py-2 rounded-lg font-medium transition-colors"
>
  Track Price
</Link>
```

Every event card on the venue page has a "Track Price" button, and every one of them links to the raw `/register` page with **no event context passed.** A user who clicks "Track Price" on "Knicks vs Celtics · Apr 28 · $120" is sent to a generic signup form that does not mention the Knicks, Celtics, or Madison Square Garden. There's no `?returnTo=/event/{id}`, no `?eventId={id}`, no `?source=venue-msg`, no context at all.

This is the biggest conversion leak on the page. The user clicked "Track Price" for a *specific event* — expressing higher intent than any other action on the site — and the product responded by showing them the same blank signup form that the homepage shows.

**Additionally:** the event card is not linked to `/event/[id]` at all. The event name is a plain `<h3>`, not a link. So an anonymous user who wants to see *what* they're signing up to track has no way to preview the event. They must register first, then navigate to find it, then track it. Three-step friction for a one-step intent.

**Fix:**

1. The event card name becomes a `<Link href={`/event/${event.id}`}>` — makes the event previewable (once event-detail soft-gate ships; until then, links to the event-detail page which redirects to `/login` with the yesterday-documented harm).
2. The "Track Price" button becomes context-preserving:

```tsx
<Link
  href={`/register?returnTo=${encodeURIComponent(`/event/${event.id}`)}&eventId=${event.id}&eventName=${encodeURIComponent(event.name)}&source=venue-${slug}`}
  className="bg-brand hover:bg-brand-dark text-white px-4 py-2 rounded-lg font-medium transition-colors"
>
  Track Price
</Link>
```

3. The register page (see form-rotation section below) must (a) honor `returnTo`, (b) render a contextual headline when `eventName` is present ("Track prices for **Knicks vs Celtics**"), and (c) write `source` into the `watchlist` record or a session cookie so acquisition attribution survives the signup flow.

4. On the event card itself, a *second* button for logged-in users: "+ Track." But the page is a server component and has no auth state — which means the `EventCard` portion of the venue page needs to be split into a client-component child that can read `useAuth()` and show either "Track Price → /register" (anonymous) or "+ Track" (opens the watchlist modal, per yesterday's spec). ~45 min refactor.

**Effort:** 1 hr standalone. Bundled with the register rewrite (below) and the shared `useWatchlistAdd` hook (yesterday's P0): 2 hrs total when done together.

**Impact:** Every "Track Price" click today arrives at `/register` cold. A contextual landing — with the event name, date, venue in the headline — is industry-standard message-match and consistently delivers +20–35% signup conversion on equivalent funnels. Compounds with the register-form rewrite to get the full lift.

### P0 (new) — Hero has no price hook. Capacity is not a reason to stay.

`venues/[slug]/page.tsx:156–173`. The hero renders:

```
{venue.name} Tickets
{venue.city}, {venue.state} - Capacity: {venue.capacity.toLocaleString()}
[Home of {team} pills]
```

That's the message: **a name, a location, a capacity, and a list of teams.** None of that is why a user Googled "Madison Square Garden tickets." The user Googled because they want to know **what's playing, when, and how much.** The page eventually tells them (in the main content area, below the fold on mobile) — but the hero, which is the page's 100%-view surface, is spent on facts that the user does not care about.

A user on a mobile-web SEO landing ticks through three decision moments in the first 3 seconds:
1. **Am I in the right place?** ("MSG Tickets" — yes, OK)
2. **What can I get?** ("Capacity: 20,000" — wrong answer)
3. **Is it worth staying?** (No price signal, no event signal, no urgency signal)

By the time the user's eye has scrolled to the event list, the message-match test has already failed.

**Fix:** Replace the capacity line with a price hook derived from the `events` array:

```tsx
const minEventPrice = events
  .filter(e => e.minPrice !== null)
  .reduce((min, e) => e.minPrice! < min ? e.minPrice! : min, Infinity);
const upcomingCount = events.length;

// In hero
<p className="text-xl text-blue-100 mb-6">
  {upcomingCount > 0 ? (
    <>
      <span className="font-semibold text-white">{upcomingCount} upcoming events</span>
      {isFinite(minEventPrice) && (
        <> · Tickets from <span className="font-semibold text-white">${minEventPrice}</span></>
      )}
    </>
  ) : (
    <>Upcoming events, price tracking, and deal alerts</>
  )}
</p>
<p className="text-sm text-blue-200 opacity-75">
  {venue.city}, {venue.state} · Capacity {venue.capacity.toLocaleString()}
</p>
```

Capacity and city drop to a muted second line. The first line becomes a price hook that passes the message-match test.

**Effort:** 25 min. **Impact:** Reduces bounce rate on SEO-landed sessions. Not independently measurable without analytics, but industry convention puts the lift at 5–12% session depth — which compounds with every downstream fix.

### P1 (new) — Seating-tier sidebar shows "~0.35x base" with no base to multiply. Meaningless to users.

`venues/[slug]/page.tsx:249–273`. The seating guide renders 4 tiers with a multiplier ("~2.5x base", "~0.35x base", etc.) but **never renders the base.** The user sees a number between 0.35 and 2.5 with "x base" next to it and has no way to translate that into dollars.

```tsx
<span className="text-sm text-gray-600">
  ~{tier.multiplier}x base
</span>
```

This is informational-design debt. The data is there (events array has min prices); the math is simple; the rendering doesn't do it.

**Fix (two options):**

**Option A (cheaper, ship today):** Change the copy to render percentages and explain the reference:

```tsx
<span className="text-sm text-gray-600">
  {Math.round(tier.multiplier * 100)}% of cheapest ticket
</span>
```

Under the list, add helper text: "Cheapest upcoming event: ${minEventPrice}. Estimated tier prices scale from this reference."

**Option B (better, 45 min):** Compute and render actual dollar ranges:

```tsx
const basePrice = Math.min(...events.map(e => e.minPrice || Infinity));
const tierPrice = Math.round(basePrice * tier.multiplier);

<span className="text-sm text-gray-600">
  ~${tierPrice}
</span>
```

Option B is the right answer if the data is reliably populated. Option A is the right answer if `minPrice` is frequently null (events with "Price TBA"). Quick check: the current template renders "TBA" often in the event list (`venues/[slug]/page.tsx:210–212`), so null-handling is non-trivial — which argues for Option A today, Option B in a follow-up when `events` data quality is higher.

**Effort:** 15 min (Option A) / 45 min (Option B). **Impact:** Converts an uninterpretable widget into a useful one. Small absolute-volume conversion impact, but material trust/comprehension benefit.

### P2 (new) — City-slug computation uses `.replace(' ', '-')` which only replaces the first space. Latent bug for any future 3+-word city name.

`venues/[slug]/page.tsx:150` and `:297`:

## Form Rotation: User Registration (`/register`)

**Formalized rewrite spec.** This form has been flagged as "carry-over" in every audit for the last 3 days without a complete spec. Today's audit closes that.

**File:** `web/src/app/register/page.tsx` (129 lines).

### Current state (what it is)

- 3 fields: email, password, confirm-password.
- `type="email"` and `type="password"` — correct keyboard on mobile ✓.
- `required` on all fields ✓.
- Client-side validation: password match + 8-char minimum ✓ (bare minimum).
- Submit calls `register(email, password)` from AuthContext, then `router.push('/dashboard')` on success.
- Error state renders as a red banner inline — no field-level error attribution.
- Loading state: button changes copy to "Creating account..." and disables.
- Already-have-account link to `/login` ✓.

### Findings

#### P0 — No `autoComplete` attributes on any input. Browser autofill broken.

Lines 65–107. No `autoComplete` attribute on email, password, or confirm-password fields. Safari, Chrome, and iOS autofill rely on this. A returning user who wants to reuse a saved credential — or a new user whose password manager wants to offer a generated password — cannot.

**Fix:**

```tsx
<input
  id="email"
  type="email"
  autoComplete="email"
  name="email"
  // ...
/>

<input
  id="password"
  type="password"
  autoComplete="new-password"
  name="password"
  // ...
/>

<input
  id="confirmPassword"
  type="password"
  autoComplete="new-password"
  name="confirmPassword"
  // ...
/>
```

Also missing: `name` attributes. Some password managers use `name` over `id`. Add for belt-and-suspenders.

**Effort:** 5 min. **Impact:** +5–15% form completion, higher on mobile where typing is costliest.

#### P0 — No `returnTo` parameter honored. Users bounced here from a deep link lose their destination.

Line 36: `router.push('/dashboard')` — hardcoded. A user who clicked "Track Price" on `/venues/msg` (once the P0 above lands) and arrives at `/register?returnTo=/event/123` will, on success, land on `/dashboard` instead of `/event/123`. Context preservation fails at the last step of the funnel.

**Fix:**

```tsx
import { useRouter, useSearchParams } from 'next/navigation';

const searchParams = useSearchParams();
const returnTo = searchParams.get('returnTo') || '/dashboard';

// In handleSubmit:
await register(email, password);
router.push(returnTo);
```

Security note: validate `returnTo` is a same-origin relative path before redirecting to prevent open-redirect. Simple check: must start with `/` and not `//`.

**Effort:** 15 min. **Impact:** Pairs with venue-page and (future) compare/event-detail contextual registrations to close the loop. Without this, every upstream contextual-link fix is half-broken.

#### P0 — No context-aware headline. Users who arrived from a specific intent see the same generic page as a cold visitor.

Line 50–55: Always renders "Create your account / Start tracking ticket prices today." When a user arrives from `/register?eventName=Knicks%20vs%20Celtics&source=venue-msg`, the headline should match the intent.

**Fix:**

```tsx
const eventName = searchParams.get('eventName');
const source = searchParams.get('source') || '';

// Derive headline
const headline = eventName
  ? `Track prices for ${decodeURIComponent(eventName)}`
  : source.startsWith('venue-')
    ? 'Get venue-specific price alerts'
    : source === 'compare'
      ? 'Save your comparison and track prices'
      : 'Create your account';

const subheadline = eventName
  ? "We'll email you the moment prices drop below your target."
  : 'Start tracking ticket prices today';
```

Then render `{headline}` and `{subheadline}`.

**Effort:** 20 min (for a basic context map). **Impact:** Message-match from referring page → registration form is high-leverage. Industry norm: +10–20% completion rate on context-matched registration forms vs. generic.

#### P0 — No source capture. Acquisition attribution is lost at the signup step.

Yesterday's Analytics ask (P1) depends on this: `source` parameter should be captured into the `users` row or into a session cookie. Today, `/register` drops it.

**Fix:** Two paths:

**Option A (cleaner, backend change):** Pass `source` into the register API call and add a `signup_source` column to `users`:

```tsx
await register(email, password, source);
```

`register()` in AuthContext passes `source` to `POST /api/auth/register`. Backend writes `signup_source` column. Migration: `ALTER TABLE users ADD COLUMN signup_source VARCHAR(100);`

**Option B (client-only, ships today):** Write `source` to a cookie on form mount, let the backend/analytics read it on subsequent requests:

```tsx
useEffect(() => {
  if (source) {
    document.cookie = `ts_source=${encodeURIComponent(source)}; path=/; max-age=2592000; SameSite=Lax`;
  }
}, [source]);
```

Recommend Option A — proper attribution. 30 min backend + 15 min frontend.

**Effort:** 45 min (Option A). **Impact:** Required for any cohort analysis once Analytics ships (Day 16). Without this column, post-hoc attribution of signups to venue/compare/event-detail/ad sources is impossible.

#### P1 — Confirm-password field is pure friction. Delete it, add a show/hide toggle.

Industry norm (Stripe, Linear, Figma) since ~2022: single password field with a show/hide eye toggle. The confirm-password field catches 0.1% typos at the cost of doubling the input friction for 99.9% of users. Worse: password managers autofill both fields identically anyway, so the "typo catch" does not actually catch typos for the users who use password managers.

**Fix:**

```tsx
const [showPassword, setShowPassword] = useState(false);

<div className="relative">
  <label htmlFor="password" className="block text-sm font-medium text-gray-700 mb-2">
    Password
  </label>
  <input
    id="password"
    type={showPassword ? 'text' : 'password'}
    autoComplete="new-password"
    required
    minLength={8}
    value={password}
    onChange={(e) => setPassword(e.target.value)}
    className="w-full px-4 py-3 pr-12 border border-gray-300 rounded-lg focus:ring-2 focus:ring-brand focus:border-transparent outline-none transition-all"
    placeholder="At least 8 characters"
  />
  <button
    type="button"
    onClick={() => setShowPassword(v => !v)}
    className="absolute right-3 top-10 text-gray-400 hover:text-gray-600 text-sm"
    aria-label={showPassword ? 'Hide password' : 'Show password'}
  >
    {showPassword ? 'Hide' : 'Show'}
  </button>
</div>
```

Delete the confirm-password field and its state. Password-match validation (line 22–25) goes with it. `minLength={8}` replaces the "at least 8 characters" manual check (line 27–30) — browser will enforce it natively.

**Effort:** 30 min (delete field + state + validation + add toggle). **Impact:** +10–15% form completion per standard industry benchmark for confirm-field removal.

#### P1 — No password-strength meter. User has no feedback on whether their password is strong enough.

Add a lightweight meter under the password field. Three buckets (weak/okay/strong) based on character class + length. No zxcvbn dependency — simple heuristic:

```tsx
function passwordStrength(pw: string): 'weak' | 'okay' | 'strong' {
  if (pw.length < 8) return 'weak';
  const classes = [/[a-z]/, /[A-Z]/, /[0-9]/, /[^a-zA-Z0-9]/].filter(re => re.test(pw)).length;
  if (pw.length >= 12 && classes >= 3) return 'strong';
  if (pw.length >= 10 && classes >= 2) return 'okay';
  return 'weak';
}
```

Display a 3-segment bar with the appropriate color. Informational only — don't block submission on "weak" (friction).

**Effort:** 30 min. **Impact:** Small — security hygiene + trust cue.

#### P1 — Error message does not distinguish "email already exists" from other errors. User cannot self-resolve.

Line 38: `setError(err instanceof Error ? err.message : 'Registration failed')`. The backend returns an error message; the frontend renders it. If the backend returns "User already exists," the user sees "User already exists" — OK, but no CTA to "Sign in instead." The most common registration error (duplicate email) should have a one-click recovery path.

**Fix:**

```tsx
{error && (
  <div className="bg-red-50 text-red-700 p-4 rounded-lg text-sm">
    <p>{error}</p>
    {error.toLowerCase().includes('exists') && (
      <p className="mt-2">
        <Link href={`/login?email=${encodeURIComponent(email)}${returnTo ? `&returnTo=${encodeURIComponent(returnTo)}` : ''}`} className="underline font-medium">
          Sign in instead →
        </Link>
      </p>
    )}
  </div>
)}
```

**Effort:** 15 min. **Impact:** Removes a stuck-state for the ~10–20% of form errors that are duplicate-email attempts.

#### P1 — No TOS/privacy fine print. Legal risk + trust gap.

Lines 110–116. The submit button has no accompanying fine print: "By creating an account, you agree to our [Terms] and [Privacy Policy]." This is both standard trust-signal copy and a legal safeguard.

**Fix:**

```tsx
<p className="text-xs text-gray-500 text-center">
  By creating an account, you agree to our{' '}
  <Link href="/terms" className="text-brand hover:underline">Terms</Link>{' '}
  and{' '}
  <Link href="/privacy" className="text-brand hover:underline">Privacy Policy</Link>.
</p>
```

(Assumes `/terms` and `/privacy` exist. Flag for Content Agent if not.)

**Effort:** 10 min (once pages exist). **Impact:** Trust signal + legal hygiene.

#### P1 — Submit button copy is "Create account." Should be benefit-framed.

Button reads "Create account" / "Creating account..." The user's desire is not "I would like to create an account" — it is "I would like to track ticket prices." Button copy should sell the outcome.

**Fix:**

Context-aware button copy:

```tsx
const buttonText = loading
  ? 'Creating your account...'
  : eventName
    ? `Start Tracking ${decodeURIComponent(eventName).slice(0, 30)}${eventName.length > 30 ? '...' : ''}`
    : source.startsWith('venue-')

```

**Effort:** 15 min (ships with P0 context-aware headline). **Impact:** +5–10% CTR on the submit button. Compounds with contextual-headline P0.

#### P2 — No Google OAuth option. Consumer-ticket competitors offer it; every missing option is friction.

Adding Google Sign-In is meaningfully more than a CRO finding — requires backend OAuth wiring, token-to-user mapping, and security review. Flag for product roadmap, not this sprint.

**Effort:** 4–8 hrs (full OAuth wiring). **Impact:** +15–25% signup rate per industry norms for consumer products. Not in this sprint.

#### P2 — Inline email-typo correction absent. "@gmial.com" silently accepted.

Common pattern: on blur, check email against a list of common typos (gmial → gmail, yaho → yahoo, hotnail → hotmail). If typo detected, render a soft suggestion: "Did you mean you@gmail.com?" One-click accept.

Low priority but removes a specific class of undeliverable-address signups. Ties into analytics quality: ghost-signups inflate funnel numbers without contributing to retention.

**Effort:** 30 min (Mailcheck-style heuristic, no external dep).
