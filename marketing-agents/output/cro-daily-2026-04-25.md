### The premise of the WC funnel

The 2026 World Cup is a **fixed-deadline, finite-supply, peak-intent surface.** Every other page on the site is evergreen — a missed conversion today on `/venues/msg` is a conversion someone else might capture next week. The WC funnel is not. Every conversion missed between today (T-47) and June 11 is a conversion forever lost. There is no "next quarter" for World Cup 2026.

This is also the **only seasonal moat the site has.** Generic ticket comparison is a crowded space; "World Cup ticket comparison built before the tournament starts" is a one-time SEO + content + paid window. Agents 1, 4, and 5 have been pouring content/SEO/ads into this surface for weeks (per git log: 5+ MetLife refresh commits this month alone; per `marketing-agents/output/ads/`, multiple WC-themed creatives shipped this week). The conversion machinery on the receiving end is unchanged from Day 7 — and is, in two specific ways, **actively hostile to the user's intent.**

The main page has **two positives** worth naming first:

1. **Truthful structured data** (lines 24–95) — `SportsEvent` + `BreadcrumbList` + an `AggregateOffer` with `lowPrice: 50`. The `lowPrice` claim is plausible for group-stage upper-deck seats and is a useful SERP-rich-result hook. No aspirational feature claims (contrast: `/dashboard` and `/compare` JSON-LD).
2. **Server-rendered + correctly indexable** with metadata exports (in both `page.tsx:6–21` and `layout.tsx:3–11`).

The stadium template has **three positives:**
1. **`generateMetadata`** ✓ (lines 16–42) — same correct pattern as `/venues/[slug]`.
2. **`StadiumOrArena` JSON-LD** with `AggregateOffer` and a *computed* `lowPrice` from the venue sections data (lines 55–62, 91–97). Smart — the price hook is data-derived, not hardcoded.
3. **Back-link to main WC page** (line 110–115) — small but real navigation polish that yesterday's venue-page audit noted was *missing* on `/venues/[slug]`.

These positives mean the WC pages are *being indexed and ranked.* The acquisition surface is operational. The conversion machinery is what's catastrophic.

The current state of the WC funnel for an anonymous user — i.e., 99%+ of arrivals from SEO, paid, and social — looks like this:

1. **Main page:** Hero stats (48/104/16/3) → "Search World Cup Tickets" → dashboard search (works) OR "View Match Schedule" → `#schedule` anchor → date picker → "Find Tickets" per match → dashboard search.
2. **Stadium page:** Hero with capacity → seating sections with prices → "Find World Cup Tickets" sidebar (dashboard search) OR "Get Price Alerts" sidebar (`/register` — promising a feature that doesn't exist).
3. **Bottom CTA on main:** "Create Free Account" → bare `/register` (no source, no returnTo, no event context).
4. **Bottom CTA on stadium:** "View All World Cup Venues" → main WC page — i.e., **a CTA that sends the user backward in the funnel.**

There is no email capture. No "Notify me when matches at this stadium go on sale." No price-watch on individual matches. No countdown framing despite T-47 days. No social proof. The user who came to the page asking "how do I get FIFA World Cup tickets?" is told: search the dashboard (which mostly returns no inventory yet, since FIFA hasn't released most match-by-match resale supply), or sign up for a feature we don't have.

### P0 (new) — No countdown to June 11 anywhere on the WC funnel. The single highest-leverage urgency cue on a fixed-deadline product is missing.

Today is 2026-04-25. Tournament kickoff is 2026-06-11. **47 days.** This number — and the daily decrementing of it — is the most powerful urgency cue available to a peak-demand seasonal product. Every day from now to June 11, this number is the user's strongest reason to act today instead of "later." It belongs above the fold on every WC page.

The main page hero (`page.tsx:108–135`) renders only a static date pill: "June 11 - July 19, 2026." It tells the user *when*, not *how soon.* The stadium page hero (`[stadium]/page.tsx:107–139`) doesn't even have the date — just country flag + city + capacity + home teams. Every WC page is **47-days-blind.**

**Fix:** Replace the static date pill on both surfaces with a live countdown component derived from the page-load date. Use a server-component-friendly approach (compute on render — accurate to the day, no hydration cost):

```tsx
// New component: web/src/components/WorldCupCountdown.tsx
const KICKOFF = new Date('2026-06-11T16:00:00Z'); // group-stage opener kick

export default function WorldCupCountdown({ className = '' }: { className?: string }) {
  const now = new Date();
  const daysToKickoff = Math.max(0, Math.ceil((KICKOFF.getTime() - now.getTime()) / 86400000));

  if (daysToKickoff === 0) {
    return <span className={className}>Tournament has begun · June 11–July 19</span>;
  }

  const tone = daysToKickoff <= 7 ? 'critical' : daysToKickoff <= 30 ? 'urgent' : 'soon';

  return (
    <div className={className}>
      <span className="font-bold text-2xl md:text-3xl">{daysToKickoff} days</span>
      <span className="text-base ml-2 opacity-90">until kickoff · June 11, 2026</span>
    </div>
  );
}
```

Mount on:
- Main page: replace line 112–114 ("June 11 - July 19, 2026" pill) with `<WorldCupCountdown />`.
- Stadium page: insert a `<WorldCupCountdown />` line above the venue title (between the country-flag bar and the `<h1>`).
- Schedule client component: optionally, a "Kickoff in N days" bar above the date picker.

**Effort:** 30 min (component + 2 mount points). **Impact:** Urgency is the largest behavioral driver on any peak-demand product, and it becomes more powerful, not less, as the deadline approaches. T-47 → T-30 → T-7 each compound. Estimated +5–15% session depth and +3–8% conversion on every WC page.

## Form Rotation: Newsletter Signup (Footer Variant)

**Critical context:** Per the regression-class P0 above, **the footer variant is not actually mounted in the global `<Footer>`.** It is rendered only on the homepage (`app/page.tsx:314`). ### Findings

#### P0 — No `autoComplete="email"`. Browser autofill broken. **Day 6 unresolved.**

Line 56–63. No `autoComplete` attribute. Returning users who want to reuse a saved email and password-manager users whose autofill would otherwise prefill the field cannot. This was a Day 6 finding (per `cro-daily-2026-04-19.md`) and remains unresolved.

**Fix:**

```tsx
<input
  type="email"
  value={email}
  onChange={(e) => setEmail(e.target.value)}
  placeholder="you@example.com"
  autoComplete="email"
  aria-label="Email address"
  className="..."
  required
/>
```

Three additions: `autoComplete="email"`, `aria-label="Email address"` (the form has a heading but no `<label>` element), and `name="email"` (some password managers use `name` rather than `id` for field detection — add for belt-and-suspenders).

**Effort:** 5 min. **Impact:** Mobile completion +8–12% per industry benchmark.

#### P0 — Loading button copy is `...`, inconsistent with other variants and uninformative. **Day 6 unresolved.**

Line 69. Button reads `...` while loading. The `inline` and `card` variants use `Subscribing...` — full word. `...` alone is ambiguous (could be a typing indicator, could be loading state, could be a stuck network request).

**Fix:** `{status === 'loading' ? 'Subscribing...' : 'Get Deals'}` — copy in line with the other variants and with the button-copy P1 below.

**Effort:** 1 min. **Impact:** Trust. Marginal.

#### P0 — No privacy reassurance below form. **Day 6 unresolved.**

The `card` variant has "No spam, unsubscribe anytime." (line 150–152). The `footer` variant has none. Users hesitate at email-capture forms without an explicit privacy reassurance — particularly on a brand they're encountering for the first time.

**Fix:** Add a one-line below the form:

```tsx
<p className="text-gray-500 text-xs mt-3">No spam. Unsubscribe any time.</p>
```

**Effort:** 5 min. **Impact:** +3–5% submit rate per industry benchmark for privacy-line addition on cold-traffic forms.

#### P0 — Button copy "Subscribe" is action-only, not benefit-led. **Day 6 unresolved (re-stated).**

Line 69. "Subscribe" is the verb the *product* is doing (adding the user to a list). The user wants the *outcome* — deals, alerts, savings. Per `form-cro` guidance: action + outcome > action alone.

**Fix:** Test "Get Deals" (default), "Get Price Alerts" (on ticket-intent surfaces), "Send Me Tips" (on blog/content surfaces). Default "Get Deals" matches the heading "Get Ticket Deals" — message-match within the form.

```tsx
<button ...>{status === 'loading' ? 'Subscribing...' : 'Get Deals'}</button>
```

**Effort:** 2 min (default change) / 30 min (A/B variant). **Impact:** +5–10% submit per industry benchmark for benefit-framed button copy.

#### P0 — Placeholder `Enter your email` is label-shaped, not example-shaped. **Day 6 unresolved.**

Line 60. Placeholders work best as *examples* (`you@example.com`), not as labels (`Enter your email`). Label-shaped placeholders disappear the moment the user begins typing, which removes context just when the user might want to reconfirm what they're entering. Example-shaped placeholders teach the format and never confuse with a label.

**Fix:** `placeholder="you@example.com"`.

**Effort:** 1 min. **Impact:** Marginal but compounds with `aria-label` (which provides the always-on label for screen readers + autofill).

#### P1 — Success state has no expectation-setting copy.

Line 53. On success, only renders `{message}` from the API response (typically a short "Subscribed!" or similar). No "First email arrives within 24 hours," no "Check your inbox," no "We'll never share your email." Users who subscribe and get a single ambiguous success line feel uncertain about what they just did.

**Fix:**

```tsx
{status === 'success' ? (
  <div>
    <p className="text-green-400 text-sm font-medium">{message}</p>
    <p className="text-gray-400 text-xs mt-2">First email arrives within 24 hours. Check your inbox.</p>
  </div>
) : (...)}
```

**Effort:** 5 min. **Impact:** Trust. Marginal direct-conversion impact, real downstream (deliverability — users who expect the email are less likely to mark it as spam).

#### P1 — No inline email-typo detection. Same finding as register-form audit yesterday.

`@gmial.com`, `@yahooo.com`, `@hotnail.com` silently accepted. Bounces and spam-marks compound on the back end. Lightweight Mailcheck-pattern (no library): on blur, check email TLD/domain against common typos and surface a one-click suggestion ("Did you mean **you@gmail.com**?").

**Fix (sketch):**

```tsx
const COMMON_TYPOS: Record<string, string> = {
  'gmial.com': 'gmail.com', 'gmaill.com': 'gmail.com',
  'yahooo.com': 'yahoo.com', 'yhoo.com': 'yahoo.com',
  'hotnail.com': 'hotmail.com', 'hotmial.com': 'hotmail.com',
  'outllook.com': 'outlook.com',
};

function suggestCorrection(email: string): string | null {
  const [local, domain] = email.split('@');
  if (!domain || !local) return null;
  return COMMON_TYPOS[domain.toLowerCase()] ? `${local}@${COMMON_TYPOS[domain.toLowerCase()]}` : null;
}

// In handleBlur, surface suggestion below the input:
{suggestion && (
  <button type="button" onClick={() => setEmail(suggestion)} className="text-xs text-brand underline">
    Did you mean {suggestion}?
  </button>
)}
```

**Effort:** 30 min. **Impact:** −30–50% undeliverable signups. Indirect — protects deliverability and downstream metrics.

#### P1 — No success-state telemetry now that GTM is wired.

Now that GTM is installed (per today's positive update), the `dataLayer` is initialized and ready. The footer form (and inline + card variants) push **no events** on submit, success, or error. The simplest possible instrumentation:

```tsx
// On success:
if (typeof window !== 'undefined' && (window as { dataLayer?: unknown[] }).dataLayer) {
  (window as { dataLayer: unknown[] }).dataLayer.push({
    event: 'newsletter_subscribe',
    newsletter_source: source,
  });
}

// On error:
window.dataLayer?.push({
  event: 'newsletter_error',
  newsletter_source: source,
  newsletter_error: message,
});
```

This is the single highest-leverage analytics-instrumentation change available right now — every variant of the form fires through the same handler, so a 5-line addition wires up site-wide newsletter telemetry. Same pattern can apply to register, login, watchlist add, and compare submission.

**Effort:** 15 min (newsletter form only) / 1 hr (full conversion-event suite across forms). **Impact:** Unblocks every "we'll measure once analytics ships" caveat in this report and prior reports. Day 17 of zero conversion telemetry can drop to Day 0 with one PR.

#### P2 — No `<label htmlFor>`. Heading is the de-facto label.

Line 48 renders an `<h4>` "Get Ticket Deals" above the form, but the input has no `<label>` and no `id`. Screen-reader users may hear the heading and the input as separate elements. Adding `aria-label="Email address"` (covered in P0 above) addresses the SR concern without needing a visible label change.

**Effort:** 0 min — covered by P0 `aria-label` addition.
