## Monday Focus: Homepage (`/`)

**File inspected:** `web/src/app/page.tsx` (354 lines, server component) and the dynamic `web/src/components/HomeHeroButtons.tsx` (49 lines, client component, **imported but unused**).

### The premise

The homepage is the single most-visited surface on the site and the destination of every blog "Subscribe" link, every footer brand-link, every back-to-home navigation, and every `ticketscan.io` direct-load. It is the **acquisition crown jewel.** Today's audit found that:

1. The hero is **statically rendered for both logged-in and logged-out users** despite a dynamic auth-aware component existing in the codebase but never being used.
2. Three of the homepage's most prominent sections (stats bar, trending deals, testimonials) publish **claims that cannot be substantiated** by the platform's current shippable infrastructure.
3. The two real-product surfaces (Popular Venues, World Cup banner) are excellent — accurate, navigable, on-brand.
4. The newsletter capture (already audited yesterday on the `card` variant) and footer NewsletterSignup remain **the only two capture surfaces on the entire site** (Day 2 carry-over from Saturday's regression-class P0).

The pattern: the homepage *advertises* a savings product that doesn't ship (price alerts), *displays* deals that don't link to events, and *quotes* testimonials about outcomes that haven't happened. The acquisition pages further down (venue, WC, blog) all face the same truthfulness audits — but the homepage is the worst offender because it sets the trust expectation for everything else.

Below: 6 new P0 findings + 4 new P1 findings on the homepage, plus a Day-9 formalization of the Price Alert setup form (today's rotation slot).

```tsx

```

Three claims:

1. **"50K+ Events Tracked"** — Plausible if `events` table has been populated by Ticketmaster Discovery API queries; needs verification against `SELECT COUNT(*) FROM watchlist` (likely closer to <100 today) versus an indexable-events-pulled count. Today this is unverified but at least directionally not impossible.
2. **"$127 Avg. Savings"** — **Unverifiable, almost certainly fabricated.** Avg savings is a number you can only compute *after* a user (a) sets a target price, (b) receives a price-drop alert, (c) buys at the alerted price, and (d) reports the savings. Step (a) requires target-price UI that doesn't exist (Day 9). Step (b) requires a price-tracking cron that fires alerts via the email bridge that doesn't query the right table (Day 8). Step (c) requires a purchase-tracking integration that doesn't exist anywhere in the repo. 3. **"5+ Sites Compared"** — Truthful but ambiguous. The product compares Ticketmaster, SeatGeek, StubHub (3 confirmed), with VividSeats listed as optional. "5+" is not factual today.

This is not a CRO issue alone — it's a **regulatory exposure issue** (FTC §5, "deceptive practices in advertising"; state consumer protection laws in CA/NY have stricter substantiation requirements for savings claims). But it is *also* a CRO issue: cold traffic is increasingly skeptical of unsourced numbers. A user who notices the savings claim, scrolls down, sees no asterisk, no "based on X data," no methodology link — registers the page as marketing-noise.

**Fix (option A — substantiate, ~30 min):** Replace with verifiable numbers from the actual database:

```tsx

// stats: { eventsTracked: number, watchlistItems: number, sitesCompared: number, lastUpdated: string }

<div><div className="text-3xl font-heading font-bold text-brand">{stats.sitesCompared}</div><div className="text-gray-500 text-xs mt-1">Ticket sites compared</div></div>
```

Where `getHomepageStats()` queries:

```sql

  (SELECT COUNT(*) FROM events_cache WHERE last_seen_at > NOW() - INTERVAL '30 days') AS events_tracked,
  (SELECT COUNT(*) FROM watchlist) AS watchlist_items,
  3 AS sites_compared;  -- Hardcoded; bump to 4 when VividSeats integration ships.
```

**Truthfulness floor:** If `watchlist_items < 50`, render an alternate stats bar that doesn't display the number ("Be among the first to track a price"); same convention as the venue/WC/blog social-proof bands.

**Fix (option B — remove, 5 min):** Delete the savings claim entirely; keep events + sites:

```tsx

'use client';

import { useEffect, useState } from 'react';

export default function WorldCupCountdown() {
  const [days, setDays] = useState<number | null>(null);

  useEffect(() => {
    const kickoff = new Date('2026-06-11T00:00:00Z');
```

## Form Rotation: Price Alert Setup (Day 9 — Does Not Exist; Formalized Today as a Design Spec)

**Critical context:** Today's form rotation slot is **Price Alert setup.** This UI does not exist anywhere in the repo. It has been promised in **5 separate places** (compare page, dashboard, 16 stadium sidebars, main WC Tip 3, main WC Why-Compare card 2) for 9 consecutive days. Yesterday's blog audit added implicit promises in the bottom-CTA copy ("track ticket prices on specific events"). Today's homepage audit added implicit promises in the price-tracker hero mock-up (which shows BUY/HOLD badges that imply a setup flow exists).

The form does not exist. There is no `<PriceAlertSetup>` component, no `<TargetPriceInput>` field on the watchlist add modal (which itself doesn't exist as a modal — Day 9), no UI affordance anywhere for the user to enter the target price that triggers the alert.

Today's review formalizes the design spec — what the form *should* look like — so that when dev capacity opens, the spec is complete.

### Spec: Inline Target-Price Capture on Watchlist Add

**Surface:** Watchlist add (today: a single `+` button on `EventCard`; should become a popover or inline expansion).

**Trigger:** User clicks "Track" or "Notify Me" on any event surface (event card, event detail, compare row, WC stadium-match row).

**Form fields (3 max):**

```tsx
<div className="bg-white border border-gray-200 rounded-xl p-5 max-w-md">
  <h3 className="font-heading font-bold text-navy text-sm mb-1">Track this event</h3>
  <p className="text-gray-500 text-xs mb-4">{event.name} · {event.date} · {event.venue}</p>

  <label htmlFor="target-price" className="block text-xs font-medium text-gray-700 mb-1">
    Notify me when the price drops to:
  </label>
  <div className="flex items-center gap-2 mb-3">
    <span className="text-gray-500">$</span>
    <input
      id="target-price"
      type="number"
      inputMode="decimal"
      value={targetPrice}
      onChange={(e) => setTargetPrice(e.target.value)}
      min={Math.floor(event.lowestKnownPrice * 0.5)}
      max={Math.ceil(event.lowestKnownPrice * 1.0)}
      step="5"
      placeholder={`${Math.floor(event.lowestKnownPrice * 0.85)}`}
      className="flex-1 border border-gray-300 rounded-lg px-3 py-2 focus:outline-none focus:ring-2 focus:ring-brand"
      autoComplete="off"
      name="target_price"
      aria-label="Target price in dollars"
    />
  </div>
  <p className="text-xs text-gray-500 mb-4">
    Current price: ${event.lowestKnownPrice}. Average over last 30 days: ${event.avg30DayPrice}.
  </p>

  {/* Anonymous flow: collect email */}
  {!user && (
    <>
      <label htmlFor="alert-email" className="block text-xs font-medium text-gray-700 mb-1">
        Email for alerts:
      </label>
      <input
        id="alert-email"
        type="email"
        value={email}
        onChange={(e) => setEmail(e.target.value)}
        placeholder="you@example.com"
        autoComplete="email"
        name="email"
        aria-label="Email address for alerts"
        required
        className="w-full border border-gray-300 rounded-lg px-3 py-2 mb-3 focus:outline-none focus:ring-2 focus:ring-brand"
      />
    </>
  )}

  <button
    type="submit"
    disabled={status === 'loading'}
    className="w-full bg-gradient-to-r from-brand to-teal text-white py-2.5 rounded-lg font-bold text-sm hover:opacity-90 transition-opacity"
  >
    {status === 'loading' ? 'Setting up alert...' : `Notify me at $${targetPrice || event.lowestKnownPrice}`}
  </button>

  <p className="text-xs text-gray-400 mt-3 text-center">
    {!user
      ? "We'll email you when the price drops. Free, no account required."
      : "Alert will be sent to your account email."}
  </p>
</div>
```

### Spec rationale (each field maps to a Day-9 unresolved finding)

1. **Suggested target-price** (placeholder = 85% of current low) — gives the user a default that's plausible (industry-typical price drops are 5–25% over a tracking window). Reduces fields needed: most users will accept the default.
2. **Min/max bounds** (50%–100% of current price) — prevents the user from setting a target below platform-floor (which would never trigger) or above current (which would trigger immediately). Reduces dead-letter alerts.
3. **Context line** ("Current price ... Average over last 30 days") — gives the user the data needed to set a sensible target without having to navigate elsewhere.
4. **Anonymous-friendly** (no register required) — captures price-watch intent at peak interest. Email-only path matches the Day 9 + WC + blog + venue findings: register is the wrong ask for first-time visitors.
5. **`autoComplete="email"` + `name="email"` + `aria-label`** — same fix as the audit findings on every other form variant (NewsletterSignup × 3, register, watchlist).
6. **Action-led button copy** — "Notify me at $X" is benefit-led + dynamic. Industry data shows benefit-led submit buttons convert 10–15% better than action-only ("Submit", "Track").
7. **Trust line below the button** — pre-empts the user's question ("what email gets sent? what if I don't have an account?"). Industry data shows trust copy below the button reduces abandonment by 5–10%.

### Backend dependencies for this form

- **`POST /api/alerts/anonymous`** — create an anonymous price alert (email-only, no account). Schema:
  ```json
  { event_id, source, min_price, target_price, email, alert_email_token (uuid) }
  ```
- **`POST /api/watchlist`** — extended to accept `target_price` field (currently accepts but ignores per Day 9 finding).
- **Cron handler** — extended to look up anonymous alerts in the new table and send via `newsletter_subscribers`-friendly drip path (Day 8 dependency).

- Backend (`POST /api/alerts/anonymous` + `POST /api/watchlist` extension + cron handler update): **3 hrs.**

- **Total: ~8 hrs / 1 dev day.**

**Per the Day 9 cross-reference: the price alert is the product's primary value proposition.** Every page on the site advertises it. Today, it ships nothing.
