## Tuesday Focus: Compare Page (`/compare`)

**File inspected:** `web/src/app/compare/page.tsx` (665 lines, client component, `'use client'`).

### The premise

The compare page is the **single most product-defining surface on the site** — the homepage hero promises "Compare. Track. Save.", every page CTA points here, every blog post recommends it, the footer Quick Links include it, the WC cluster's value-prop is built around it, and the brand promise ("we compare ticket prices across Ticketmaster, SeatGeek, StubHub, and more") is *the* compare functionality.

This page is also the **strongest cold-traffic activation surface the platform has** — a visitor who has never used TicketScan can, in theory, type "Magic" into the keyword box, hit Compare Prices, see real-time prices from two sources side-by-side, observe a "Save $42" badge, and form an opinion about the product within 10 seconds. That moment is the *most efficient possible activation event*.

Today, that moment is unreachable. **The page hard-redirects every unauthenticated visitor to `/login` on mount** — before they see a single comparison, before they understand what the page does, before they have any reason to commit to an account. This is a 14-day-old finding that has not been touched.

But beyond the gate, the page itself has **multiple other CRO failures**:
- Every successful comparison ends with the user clicking out to Ticketmaster or SeatGeek — the "Buy on X" buttons leak the user with **zero analytics signal fired**, **zero re-engagement hook** (no "track this for me" CTA), and **zero attribution surviving the click**.
- The empty state and social-proof rail mention four sources (TM, SG, StubHub, Vivid Seats); the *actual* result columns show only two.
- The "All Events" view exposes internal debug copy (`API may be pending approval`) to end users.
- The view toggle, sort order, and filter state are not URL-encoded — comparisons are not shareable.
- No filter for "events with savings only," no sort by savings amount.
- The single most valuable on-page signal — the "Save $X" badge on matched events — sits on a card with **no track/notify CTA**, so the user with the highest demonstrated price-sensitivity has no way to act except to leave the site.

Below: 1 P0 carry-over (the gate, Day 14) and **7 new P0/P1 findings** identified in today's review.

```tsx
  event: MatchedEvent,
  ce: CompareEvent,

    (window as { dataLayer: Record<string, unknown>[] }).dataLayer.push({
      event: 'compare_buy_clicked',
      source,
      event_id: ce.id,
      event_name: ce.name,
      event_date: ce.date,
      venue: ce.venue,
      city: ce.city,
      price: ce.minPriceWithFees ?? ce.minPrice,
      savings: event.savings,
      is_best: event.bestSource === source,
    });
  }

// In the link:
<a
  href={event.ticketmaster.url}

  rel="noopener noreferrer"

</a>
```

### P1 (new) — No "events with savings only" filter and no "sort by savings" option. The platform's strongest signal is buried in render order.

Two simple toggles would fix this:

**Fix (45 min):**

```tsx
const [filterMode, setFilterMode] = useState<'all' | 'savings'>('all');
const [sortMode, setSortMode] = useState<'date' | 'savings'>('date');

const visibleMatched = useMemo(() => {
  let m = matchedEvents;
  if (filterMode === 'savings') {
    m = m.filter(e => e.savings && e.savings > 0);
  }
  if (sortMode === 'savings') {
    m = [...m].sort((a, b) => (b.savings || 0) - (a.savings || 0));
  } else {
    m = [...m].sort((a, b) => (a.date || '').localeCompare(b.date || ''));
  }
  return m;
}, [matchedEvents, filterMode, sortMode]);
```

### Form quality findings (would apply once mounted)

`NewsletterSignup.tsx` lines 45–78 (the footer variant). The form quality is generally good but has 5 fixable improvements:

#### 1. Missing `autoComplete="email"` on the input (line 56–62)

```tsx
<input
  type="email"
  value={email}
  onChange={(e) => setEmail(e.target.value)}
  placeholder="Enter your email"
  className="..."
  required
/>
```

No `autoComplete="email"` attribute. Browsers and password managers don't recognize this as the canonical email field. Mobile users get a generic text-input keyboard layout instead of the email-optimized layout (with `@` and `.com` keys promoted).

**Fix:** add `autoComplete="email"` and `inputMode="email"` (and `name="email"` for traditional password-manager compat):

```tsx
<input
  type="email"
  name="email"
  autoComplete="email"
  inputMode="email"
  value={email}
  onChange={(e) => setEmail(e.target.value)}
  placeholder="you@example.com"
  className="..."
  required
  aria-label="Email address for ticket deals newsletter"
/>
```

**Effort:** 2 min. **Impact:** ~5–15% reduction in time-to-submit on mobile (autofill works); ~5% reduction in bounce on the input field. Same fix recommended on the `inline` and `card` variants too — the form file has three variants, all of which share this finding (Day 7 carry-over from register-form audit).

#### 2. Placeholder is generic; "Enter your email" provides no benefit hint

The placeholder ("Enter your email") describes *what* to enter but not *why*. The footer variant already has a clear above-input pitch ("Subscribe for exclusive deals and price drop alerts.") — the placeholder can reinforce or be more action-oriented.

**Fix (2 min):** `placeholder="you@example.com"` (a value-shaped placeholder instead of a label-shaped one). Reinforces that the input expects an email address; lets the surrounding copy do the persuasion.

**Effort:** 2 min. **Impact:** Marginal but additive.

#### 3. Submit button text "Subscribe" is generic; no benefit phrasing

`NewsletterSignup.tsx:69`:

```tsx
{status === 'loading' ? '...' : 'Subscribe'}
```

"Subscribe" is action-led, not benefit-led. Industry data: benefit-led submit copy ("Get deals", "Send me deals") converts ~5–15% better than action-only ("Subscribe", "Submit").

The `inline` variant already uses "Get Deals" (line 102). The footer variant should match.

**Fix (1 min):** `{status === 'loading' ? '...' : 'Get Deals'}`. Or, slightly stronger: `'Send me deals'`.

**Effort:** 1 min. **Impact:** +5–15% on submit-rate, additive on top of mount.

#### 4. Loading state is just `'...'` with no spinner; minimal feedback

Line 69: `{status === 'loading' ? '...' : 'Subscribe'}` shows a three-dot ellipsis as the only loading-state indicator. No spinner, no aria-live announcement, no time-based "Subscribing..." text. On a slow network, the user may not realize the form is processing and may double-tap.

**Fix (5 min):** A small inline spinner + visible-text:

```tsx
<button
  type="submit"
  disabled={status === 'loading'}
  className="..."
>
  {status === 'loading' ? (
    <span className="flex items-center gap-1.5">
      <span className="inline-block w-3 h-3 border-2 border-white/40 border-t-white rounded-full animate-spin" aria-hidden="true" />
      Sending...
    </span>
  ) : (
    'Get Deals'
  )}
</button>
```

**Effort:** 5 min. **Impact:** Reduces double-submit risk on slow networks. Marginal CRO impact, meaningful UX-quality gain.

#### 5. Error and success messages have no `aria-live` region; screen readers miss the announcement

Lines 73–75:

```tsx
{status === 'error' && (
  <p className="text-red-400 text-sm mt-2">{message}</p>
)}
```

The error message appears in the DOM but is rendered without an `aria-live="polite"` (or `role="status"` / `role="alert"`) region. Screen-reader users won't be notified that their submission failed.

**Fix (2 min):**

```tsx
<p
  className="text-red-400 text-sm mt-2"
  role="alert"
  aria-live="assertive"
>
  {message}
</p>
```

And on the success path (line 53):

```tsx
<p
  className="text-green-400 text-sm"
  role="status"
  aria-live="polite"
>
  {message}
</p>
```

**Effort:** 2 min. **Impact:** Accessibility compliance (WCAG 2.1 AA — Status Messages). Indirect CRO impact via inclusivity.

#### 6. No `dataLayer.push` on success — Day 20 carry-over

`NewsletterSignup.tsx:31–34`:

```tsx
if (data.success) {
  setStatus('success');
  setMessage(data.message);
  setEmail('');
}
```

No `dataLayer.push({ event: 'newsletter_subscribed', source, ... })`. Same finding as the compare-buy click finding earlier today and the broader Day-20 zero-conversion-telemetry escalation.

**Fix (3 min):** Insert before `setStatus('success')`:

```tsx
if (typeof window !== 'undefined') {
  (window as { dataLayer?: Record<string, unknown>[] }).dataLayer = (window as { dataLayer?: Record<string, unknown>[] }).dataLayer || [];
  (window as { dataLayer: Record<string, unknown>[] }).dataLayer.push({
    event: 'newsletter_subscribed',
    source,
    variant,
  });
}
```

**Effort:** 3 min. **Impact:** Once mounted in the global Footer, this push fires on every page's footer subscription — the highest-volume capture event on the site (post-mount). Compounds with the homepage card mount (already live) and the eventual blog/WC/venue inline mounts.
