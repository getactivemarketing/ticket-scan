## Thursday Focus: Event Detail (`/event/[id]`)

**File inspected:** `web/src/app/event/[id]/page.tsx` (357 lines, client component, `'use client'`).
**Supporting components inspected:** `web/src/components/BuyRecommendation.tsx` (130 lines), `web/src/components/PriceChart.tsx`, `web/src/components/PriceTrendIndicator.tsx`.

### The premise

`/event/[id]` is the platform's **decision surface.** Every other page in the funnel (`/dashboard`, `/compare`, `/watchlist`, venue pages, World Cup stadium pages) routes a user *into* this page when they want the deepest information about a single event: full price history, trend, buy recommendation, tier-by-section pricing, and (notionally) an alert/target-price interface.

This is the page where a user moves from **browsing** to **deciding.** The recommendation banner at the top says, in green, "Good Time to Buy" with high confidence — and then the page shows the user nothing they can buy.

This is also the page where the platform's three uniquely valuable features actually surface together: price-with-fees disclosure (Apr 18 ship `8a1691c`), tier breakdown (Apr 18 ship `297e29d`), and the buy/wait/hold algorithm. **More technical work has shipped on this page than any other in 2026.** None of it converts, because the page is locked behind a hard gate (Day 14) and has no buy CTA, no edit-target UI, no remove-from-watchlist, no event-date display, and no analytics.

Today's audit finds: **the engineering is solid, the wrapper is broken at every conversion seam.** Eight carry-over P0s from the prior Thursday audit (Day 14) plus seven new P0/P1 findings (most prominently: the page tells users to buy and gives them no link to a checkout).

Below: 8 carry-over findings (Day 14) and **7 new P0/P1/P2 findings** identified in today's review.

### P0 (NEW — most critical) — `/event/[id]` shows a "Good Time to Buy" recommendation but has **no Buy Tickets CTA anywhere on the page**

`event/[id]/page.tsx:228–237` (BuyRecommendation render) followed by chart and table — no Buy CTA in between, before, after, or in the header.

```tsx
{/* Buy Recommendation */}
{recommendation && (
  <div className="mb-6">
    <BuyRecommendation
      action={recommendation.action}      // 'buy_now' | 'wait' | 'hold'
      confidence={recommendation.confidence}
      reason={recommendation.reason}
      stats={recommendation.stats}
    />
  </div>
)}
```

`BuyRecommendation.tsx:57–127` renders the green "Good Time to Buy" banner — and inside that banner, **no link, no button, no CTA.** The user is told the price is good. Then they're shown a chart. Then a table. Then nothing.

The platform's core value proposition is *"we tell you the optimal time to buy."* The user reaches this page, sees green "Good Time to Buy" with high confidence, and... navigates back to `/watchlist` (the only on-page link), opens a new tab, retypes the event name into Ticketmaster or SeatGeek, and re-finds the listing. **The platform's recommendation is not shoppable.**

This has at least three structural causes:

1. **`watchlist` table doesn't store `event.url`.** Per `CLAUDE.md` schema: `watchlist (id, user_id, event_id, event_name, event_date, venue, city, target_price, created_at)` — no `event_url`. When the user originally added to watchlist from `/dashboard` (where EventCard *has* `event.url`), the URL was never persisted. The frontend has no way to surface the original Ticketmaster/SeatGeek deeplink on this page.
2. **Backend `/api/prices/recommendation` doesn't return source URLs.** The recommendation endpoint returns price stats and an action, but not the live Ticketmaster/SeatGeek event URL. So even if the frontend wanted to build a "Buy on Ticketmaster" button from the recommendation response, the data isn't there.
3. **`BuyRecommendation` component has no `cta` prop.** Even if the data existed, the component would need to accept and render a CTA.

**Fix (full path, ~3 hrs across backend + frontend):**

**Backend (1.5 hrs):**

- Add migration: `ALTER TABLE watchlist ADD COLUMN ticketmaster_url TEXT, ADD COLUMN seatgeek_url TEXT, ADD COLUMN stubhub_url TEXT;`
- Update `POST /api/watchlist` to accept and persist source URLs (frontend EventCard has `event.url`; pass it along).
- Backfill: a one-shot script that re-resolves each existing watchlist row to current TM/SG URLs (best-effort; Day 14+ rows can be left null and surfaced as "search Ticketmaster for this event" links).
- Update `GET /api/prices/recommendation/:eventId` (and `/api/prices/history/:eventId`) to include `sources: { ticketmaster_url, seatgeek_url, stubhub_url, latest_min_price_with_fees, ... }` per source.

**Frontend (1.5 hrs):**

- Update `BuyRecommendation` props to accept `sources?: { name: string, url: string, priceWithFees: number }[]`.
- Inside the green/amber/blue panel, after the stats grid, render:

```tsx
{sources && sources.length > 0 && (
  <div className="mt-5 pt-4 border-t border-current/10">
    <p className="text-sm font-medium text-gray-700 mb-3">Buy now:</p>
    <div className="flex flex-wrap gap-2">
      {sources.map(s => (
        <a
          key={s.name}
          href={s.url}
          target="_blank"
          rel="noopener noreferrer"
          onClick={() => pushDataLayer({
            event: 'event_detail_buy_clicked',
            source: s.name,
            event_id: eventId,
            recommendation_action: action,
            confidence,
            price_with_fees: s.priceWithFees,
          })}
          className="inline-flex items-center gap-2 px-4 py-2 bg-white border-2 border-current/20 hover:border-current/40 rounded-lg font-medium text-gray-900"
        >
          <span>{s.name === 'ticketmaster' ? 'Ticketmaster' : s.name === 'seatgeek' ? 'SeatGeek' : 'StubHub'}</span>
          <span className="text-sm text-gray-500">${s.priceWithFees.toFixed(0)}</span>
        </a>
      ))}
    </div>
  </div>
)}
```

**Effort:** 3 hrs (1.5 backend + 1.5 frontend). **Impact:** Closes the **single most product-broken gap on the platform.** The recommendation is the platform's value proposition; today it's a dead-end opinion. With sources, it's a shoppable comparison.

**Estimated conversion impact:** Once the hard gate is also softened (P0 Day 14 below), this is plausibly the difference between **0%** and **5–15%** of `/event/[id]` page-views producing an attributed buy click. Every dollar of paid traffic that lands here today is wasted at the recommendation; this fix is the platform's largest single revenue-correlation lift available.

**Blocker / dependency:** Requires the `pushDataLayer` helper (Wed's recommended ship). And requires the watchlist schema migration (sequencing: schema → backfill → endpoint update → component update).

#### 1. No `autoComplete` attributes on email or password fields

`register/page.tsx:69–77` (email), `84–91` (password), `99–107` (confirm). None has `autoComplete`. Modern password managers (1Password, Apple Keychain, Bitwarden, Chrome Autofill) cannot suggest a saved email or generate a strong password — meaning users either retype known emails (typo risk) or skip the form entirely.

**Fix (3 min):**

```tsx
<input id="email" name="email" type="email" autoComplete="email" inputMode="email" ... />
<input id="password" name="new-password" type="password" autoComplete="new-password" ... />
<input id="confirmPassword" name="confirm-new-password" type="password" autoComplete="new-password" ... />
```

The `inputMode="email"` triggers the email-style keyboard on mobile (`@` and `.` accessible without modifier).

**Effort:** 3 min. **Impact:** Mobile autofill and password manager support. Industry data: 5–15% completion rate lift.

#### 2. No `name` attributes — password managers can't recognize fields

#### 3. No `?returnTo=` honor — registration always redirects to `/dashboard`

`register/page.tsx:36`:

```tsx
await register(email, password);
router.push('/dashboard');
```

This is the **single most expensive line of the funnel** today. Every fix recommended Wed (dashboard banner returnTo, EventCard modal returnTo) and today (event-detail soft-gate returnTo, event-detail back-link returnTo) is **load-bearing on this line being changed.**

**Fix (15 min):**

```tsx
const searchParams = useSearchParams();
const returnTo = searchParams.get('returnTo') || '/dashboard';
const intent = searchParams.get('intent');
const eventId = searchParams.get('event_id');

// Inside handleSubmit, after register:
await register(email, password);

    // non-blocking — registration succeeded
  }

router.push(returnTo);
```

**Effort:** 15 min. **Impact:** Closes the auth-boundary context-loss gap across **all** referrers (dashboard banner, EventCard modal, event-detail soft-gate, blog CTAs, footer CTA when shipped, ad-creative deep links). Single highest-leverage register-form fix on the backlog.

#### 4. No source / referrer capture

The `/api/auth/register` endpoint (per `index.js`) doesn't accept a `source` field, so the `users` table doesn't know whether the registration came from `/dashboard`, `/event/[id]`, a blog CTA, an ad campaign, or a homepage card. **Acquisition attribution is invisible.**

**Fix (30 min):**

- Migrate `users` table: `ALTER TABLE users ADD COLUMN registration_source TEXT, ADD COLUMN registration_intent TEXT;`
- Update `POST /api/auth/register` to accept and persist `source` + `intent`.
- Update `register()` in `AuthContext.tsx` to pass `source` (read from URL params: `?from=...&utm_source=...&utm_campaign=...`).
- Front-end `register/page.tsx` reads `searchParams.get('from') || searchParams.get('utm_source') || document.referrer` and passes it on submit.

**Effort:** 30 min. **Impact:** First per-source registration attribution. Pairs with Wed's `dataLayer.push` requests so analytics can join `users.registration_source` to GA4 traffic-source data.

#### 6. No password-strength indicator beyond the 8-character minimum

`register/page.tsx:27–29`:
