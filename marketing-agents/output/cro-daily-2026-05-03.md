## Form Rotation: Newsletter signup (footer variant)

**The form spec exists. The form is not in the DOM.** Today's rotation is an audit of the third "phantom form" in three days (after price-alert and the `<Link>`-as-Subscribe blog buttons).

The component (`NewsletterSignup.tsx:45–78`) ships with a `footer` variant that is purpose-designed for the global footer:

- Dark background-friendly (the form sits on `bg-gray-800` with `bg-gray-700` border — drops cleanly into the existing `bg-gray-900` `Footer.tsx`)
- Compact horizontal layout (input + button on one row, `flex gap-2`)
- White heading + gray-400 secondary text matches the existing footer typography
- Submit button uses `bg-brand` (the platform's primary CTA color)
- Loading state: button copy collapses to `'...'` (graceful)
- Error state: `text-red-400` line below the form (graceful)
- Success state: replaces the form entirely with `<p className="text-green-400">{message}</p>` (graceful)

### 5 findings on the footer-variant form

#### P0 (NEW today) — The form is not mounted in `Footer.tsx`. The form is not mounted anywhere outside the homepage. The *footer variant specifically* exists for a footer that does not import it. Day 9 of regression.

Already covered above. Fix: 5 minutes. The fix is the same fix as Apr 25 (Day 9). The cost is the same cost. The recommendation is the same.

#### P0 (NEW today) — The form's `source` prop is not validated against any allowlist on the API side. The `index.js` `/api/newsletter/subscribe` handler stores whatever string the client sends as `newsletter_subscribers.source`. Combined with no per-mount `source` attribution discipline, this means we are accumulating an unconstrained set of `source` values across deployments and **cannot reliably segment a "where did the email come from" report.**

Specifically, the existing two homepage mounts use `source="homepage"` and `source="footer"`. If the global Footer.tsx is fixed today with `source="site-footer"`, we now have **two distinct strings competing for the same semantic meaning** (`"footer"` from the homepage's inline footer block at `page.tsx:314`, and `"site-footer"` from the global Footer.tsx). The two collide in the same column.

**Fix (15 min):**

1. **Rename the homepage inline-footer mount** at `page.tsx:314` from `source="footer"` to `source="homepage-footer"` to make it unambiguous.
2. **Use `source="site-footer"`** when adding the mount to global Footer.tsx (different scroll depth, different page context, deserves a distinct value).
3. **Add a `SOURCES` const** at the top of `NewsletterSignup.tsx` enumerating known sources (e.g., `'homepage' | 'homepage-footer' | 'site-footer' | 'blog-index' | `blog-${slug}` | `world-cup` | `world-cup-${stadium}` | 'register-skip' | 'inline'`) so the next mount has a single source of truth.

The TypeScript discipline on `source` will pay for itself within one week of analytics being live (which itself is gated on the `dataLayer` work, but the analytics dashboard will read `newsletter_subscribers.source` as the eventual segmentation column anyway).

#### P1 (NEW today) — The footer variant has **no honeypot or rate limiting on the client side, and no client-side debouncing of submit clicks.** A user who taps Subscribe twice in quick succession sends two POSTs; the API likely deduplicates by email, but the second POST will return an "already subscribed" error and the form will flip from `loading` → `error` instead of staying on `success`. UX papercut.

**Fix (10 min):** Disable the button immediately on submit via `setStatus('loading')` (already done via `disabled={status === 'loading'}` — confirmed at line 66) but also wrap the form in `<form onSubmit={...}>` with `noValidate` and add a `onSubmit` guard `if (status !== 'idle') return;` at the top of `handleSubmit`. The current code does this implicitly via the disabled state, but a fast double-tap before React re-renders can still fire two requests. The guard is defense-in-depth.

A second smaller fix — the success message that replaces the form (line 53–54) does not include a "subscribe another email" reset action. A user who subscribes from a friend's device cannot easily subscribe their own email after; they have to refresh the page. Add a `<button onClick={() => setStatus('idle')}>Subscribe another email</button>` link below the success message (~3 min).

#### P1 (NEW today) — No `dataLayer.push({event: 'newsletter_subscribed', source})` on success. (Day 25 of zero conversion telemetry.) The footer variant is the highest-volume mount the platform will ship — every non-homepage page would carry it once Day 9 is fixed — and it would generate the platform's first measurable conversion event at scale.

**Fix (3 min):** Right after `setStatus('success')` on line 32:

```tsx
if (typeof window !== 'undefined' && (window as { dataLayer?: unknown[] }).dataLayer) {
  (window as { dataLayer: Record<string, unknown>[] }).dataLayer.push({
    event: 'newsletter_subscribed',
    source,
  });
}
```

The 3 minutes of work here pays back every paid-traffic dollar by giving the marketing team the first measurable conversion event the platform will ever produce. Composes with the GTM bootstrap that has been wired (and idle) in `app/layout.tsx` for 25 days.

#### P2 (NEW today) — Footer variant heading "Get Ticket Deals" (line 48) is generic; no specificity, no value framing, no urgency. The card variant uses "Never Miss a Deal" + "Get exclusive ticket deals, price drop alerts, and tips" (more specific, more compelling). Footer should at least match the card's framing density.

**Fix (5 min, copy-only):** Heading from `Get Ticket Deals` → `Save on Every Event` (or A/B candidate `Beat Ticket Prices`). Body from `Subscribe for exclusive deals and price drop alerts.` → `Free weekly tips on finding the cheapest tickets — no spam, unsubscribe anytime.` (Removes the "exclusive deals" promise we don't yet deliver, replaces with a literal description of what subscribers receive.)

Hand off to Content Agent for an A/B test once #1/#2 above are merged and the footer is actually rendered somewhere.
