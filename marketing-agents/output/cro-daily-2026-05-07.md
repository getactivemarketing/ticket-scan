#### P1 (NEW today) — `BuyRecommendation` component renders `stats.targetPrice` even though no UI to set it exists. The recommendation **silently degrades** when `targetPrice = NULL` (which is 100% of rows today, per yesterday's `EventCard.tsx:43–49` finding). The user sees "Good Time to Buy" with no anchor for *what they were trying to pay.*

`event/[id]/page.tsx:228–237` passes `recommendation.stats` straight into `BuyRecommendation`. Per the recommendation algorithm in `CLAUDE.md`:

```javascript
if (currentPrice <= lowestRecorded * 1.05) return "buy_now"  // Within 5% of lowest
if (currentPrice >= avgPrice * 1.20) return "wait"           // 20%+ above average
if (daysUntilEvent <= 7) return "buy_now"                    // Event soon
if (currentPrice <= targetPrice) return "buy_now"            // Target hit  ← NEVER REACHED
return "hold"  // Default
```

The fourth rule (`currentPrice <= targetPrice`) is **dead code** for the entire user base — every row has `target_price = NULL`, so the comparison is `currentPrice <= null`, which JavaScript coerces to `false`. The recommendation algorithm is running with **80% of its decision logic disabled** for every user on every event.

The rendered output is *technically* correct ("buy_now" via lowest-price proximity, or "hold" by default) but **the user-personalized rule is structurally invisible.** The platform's claimed differentiator — "buy/wait/hold tuned to *your* price" — has never functioned for a single user.

This compounds with yesterday's NEW P0 #2 (EventCard `targetPrice` payload omission). Today's framing makes the downstream impact concrete: **even when the inline-target-price input ships (yesterday's 30-min spec), the BuyRecommendation rule that uses it has been silently no-op-ing for the entire history of the platform.**

**Fix (5 min, after yesterday's inline target-price input ships):** None required at the BuyRecommendation level — once `target_price` is non-null, the existing algorithm starts firing rule #4. But the platform should add a `dataLayer.push({ event: 'recommendation_personalized', target_price, current_price, action })` so the first time rule #4 fires for a real user is *measured.*

The bigger fix at the `event/[id]` surface is **rendering the personalized vs. default state explicitly** — currently the `BuyRecommendation` panel shows "Good Time to Buy" identically whether the recommendation was triggered by the lowest-price proximity rule or by the user's target-price rule. The user can't tell which.

**Render addition (10 min):**

```tsx
{recommendation.stats?.targetPrice && recommendation.action === 'buy_now' && (
  <p className="mt-3 text-sm text-green-700 font-medium">
    ✓ Tickets are at or below your target of ${recommendation.stats.targetPrice}.

{!recommendation.stats?.targetPrice && (
  <p className="mt-3 text-sm text-gray-600">
    Set a target price to get personalized recommendations.
    <button onClick={openTargetPriceModal} className="text-brand hover:underline ml-1">
      Set target →
    </button>

```

This makes the "personalize me" affordance discoverable on the surface where it belongs.

**Effort:** 15 min total (5 min analytics + 10 min render). **Impact:** First time the user understands the recommendation is differentiated *for them.* Compounds with yesterday's inline-target-price input + the 4/30 target-price-modal spec.

#### P1 (NEW today) — Email validation is implicit (`type="email" required`). The form accepts `a@b` and `you@example.com` (the actual placeholder text!) without client-side feedback. Spam-bot and low-intent registrations leak through without ever hitting the backend.

`register/page.tsx:69–77` (the email input) relies entirely on `type="email" required` for validation. HTML5 `type="email"` accepts strings like `a@b` (no TLD) and even submits the placeholder text if the user blanks the field after seeing it, depending on browser. There is no length minimum, no domain validation, and no rate limit.

The 4/30 audit (P0 #4 "no source / referrer capture") framed this as an attribution gap. Today's framing extends it to a **quality gap**: a user who copy-pastes the placeholder, or a bot scraping the form, can submit successfully. The `users` table accepts the row. The drip campaign fires (assuming the source-table bug ever ships — Day 18). The result is a poisoned drip pipeline.

**Fix (10 min):**

```tsx
const validateEmail = (email: string): string | null => {
  const trimmed = email.trim().toLowerCase();
  if (trimmed === 'you@example.com') return 'Please enter your real email address';
  if (!/^[^\s@]+@[^\s@]+\.[^\s@]{2,}$/.test(trimmed)) return 'Please enter a valid email address';
  if (trimmed.length > 254) return 'Email address is too long';
  return null;
};

// In handleSubmit, before the password check:
const emailError = validateEmail(email);
if (emailError) {
  setError(emailError);
  return;
}
```

**Effort:** 10 min. **Impact:** Closes the obvious leak. Server-side validation is still required (existing code may not validate either; `index.js` should be re-audited as a pair).
