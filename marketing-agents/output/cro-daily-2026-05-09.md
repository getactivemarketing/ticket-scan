#### P1 (NEW today) — `WorldCupSchedule.tsx:115` `filteredMatches.slice(0, 20)` truncates the list to 20 matches in the date view with a footer message that only shows in the round view ("Showing first 20 matches. The condition `scheduleView === 'round'` excludes the date view from the footer entirely. The cheaper fix: either (a) raise the limit to the actual tournament size (104 matches; the data is already fully loaded into memory client-side from `worldCupSchedule`), or (b) add a "Load more matches" button that incrementally adds 20 more on click, or (c) page the list. The page is not server-rendered (it's marked `'use client'`), so SSR cost is not a factor; the truncation appears to exist as a defensive UX limit, not a performance constraint.

**Fix (15 min):**

```tsx
const VISIBLE_LIMIT = 30;
const [showAll, setShowAll] = useState(false);
const visibleMatches = showAll ? filteredMatches : filteredMatches.slice(0, VISIBLE_LIMIT);

// in the render:
{visibleMatches.map(...)}

{filteredMatches.length > VISIBLE_LIMIT && !showAll && (
  <button
    onClick={() => setShowAll(true)}
```

#### P2 (NEW today) — The 4/25 audit's truthful-structured-data positive observation (the `SportsEvent` JSON-LD with all 16 venue locations on `page.tsx:24–76`) **omits the canonical AggregateOffer detail that would unlock event-pricing rich results**: a `highPrice` and a non-trivial `lowPrice` per the schema spec. The current schema has `lowPrice: '50'` (line 74) — a hard-coded string with no source-of-truth and no `highPrice`. Schema validators likely accept this; AI-search citation systems and Google's increasingly strict structured-data pipelines may not.

`page.tsx:69–75`:

```tsx
offers: {
  '@type': 'AggregateOffer',
  url: 'https://ticketscan.io/world-cup-2026',
  availability: 'https://schema.org/InStock',
  priceCurrency: 'USD',
  lowPrice: '50',
},
```

`'50'` as a string is technically valid; Google's preferred format is a number. `availability: 'InStock'` is making a claim the platform cannot back today (there is no live inventory aggregation across venues that produces a single "in-stock" boolean). `lowPrice: 50` is plausible for a single match at the lowest tier but is **misleading at the AggregateOffer level**, which is supposed to represent the lowest price across the *entire offer aggregate* — i.e., the cheapest available WC ticket anywhere across 104 matches. Without a verified source, this becomes another schema-lie shape (the venue page schema-half from 5/8 vs. this WC schema-soft-claim).

**Fix (10 min):**

Either:
1. **Remove the `offers` block entirely** and let the `SportsEvent` schema render without an `AggregateOffer` (preserves accuracy; loses the rich-result eligibility). Or:
2. **Source `lowPrice` from the lowest `priceRange` value across all 16 venues' `worldCupVenues[*].sections`** (which the stadium template's `extractLowestPrice()` at `[stadium]/page.tsx:55–62` already does for individual venues). **Same logic, applied across all 16 venues, produces a defensible aggregate.** Add `highPrice` from the same source (the highest price across the highest-tier section of the highest-priced venue). Remove the `availability` claim — it's not defensible at this scope until live inventory exists.

The right fix is option 2 because the data is in `worldcup.ts` already; the `extractLowestPrice` pattern is established; the schema becomes defensible.

**Effort:** 10 min. **Impact:** Removes the platform's last unmaintained schema string; aligns the WC main page schema with the truthful-structured-data principle the 4/25 audit praised; positions for Google Events rich-result eligibility once the per-match Event schema ships (cross-cut to 5/8's NEW P0 venue Event JSON-LD pattern, which is the same shape applied to a different surface).
