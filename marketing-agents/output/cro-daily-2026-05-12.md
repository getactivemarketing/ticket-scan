### What's new today (Tuesday-cycle Day 14, 4 NEW)

#### P0 (NEW today) — **The register-form `router.push('/dashboard')` at `register/page.tsx:36` short-circuits the entire `?returnTo=` chain that finding #12 from 5/5 specified.**

The 5/5 audit's spec asked for `compare/page.tsx:88` to construct a `?returnTo=/compare?city=…&keyword=…` param and pass it to `/login`. The 5/5 audit then noted "and on the login page (out of scope today, but flagging for the dev backlog): respect `returnTo` after successful auth."

Today's form-rotation re-read of `register/page.tsx` reveals **the same gap is in the register form** — and unlike `/login` (which the user *might* land on if they already have an account), `/register` is where every gate-bounced compare-page visitor goes if they want to actually use the product. **The destination is hard-coded at line 36:**

```tsx
// register/page.tsx:34–36
try {
  await register(email, password);
  router.push('/dashboard');
```

**Even if the 5/5 P0 #3 spec ships and `compare/page.tsx:88` correctly constructs `?returnTo=/compare?city=Miami&keyword=Taylor`**, and **even if `/login` is patched to respect `returnTo` after successful auth**, the user who clicks "create account" instead of "sign in" lands on `/register`, fills the form, submits, and is unconditionally bounced to `/dashboard`. The intent is destroyed at the third hop, after surviving the first two.

This is the **single most expensive intent-leak on the platform from a code-volume perspective:** ~1.5 hrs of `?returnTo=` plumbing across `compare/page.tsx` and `/login` would be undone by 1 line on `register/page.tsx:36`. The full fix requires `/register` to:
1. Read `searchParams.get('returnTo')` on mount.
2. Forward it as a query param on the "Already have an account? Sign in" link (line 121).
3. On successful registration, `router.push(searchParams.get('returnTo') || '/dashboard')`.

**Fix (5 min):**

```tsx
// register/page.tsx, top of component:
const searchParams = useSearchParams();
const returnTo = searchParams.get('returnTo');

// In handleSubmit:
await register(email, password);
router.push(returnTo || '/dashboard');

// In the JSX, line 121:
<Link href={`/login${returnTo ? `?returnTo=${encodeURIComponent(returnTo)}` : ''}`} className="text-brand hover:text-brand-dark font-medium">
  Sign in
</Link>
```

The mirror change in `/login/page.tsx` is required for the chain to close end-to-end. Both files need to be edited in the same commit; without one, the other half of the plumbing produces no observable behavior.

**Impact:** Closes the only remaining hop where compare-page intent is silently destroyed. Composes with the 5/5 P0 #3 spec on `compare/page.tsx:88`. **15 min total across all three files (compare, login, register).**

#### P0 (NEW today) — **The register form at `register/page.tsx:9–129` has zero `?source=` capture.** This is the upstream half of the cross-site source-attribution finding from 5/5 (P0 #2) — even if every CTA on the platform appends `?source=foo` to the `/register` URL, the register form ignores the param and the post-register `dataLayer.push` (when finding from 4/26 ships) has nothing to push.

This composes with the `?returnTo=` finding above. A correct register form reads **both** params on mount, forwards both on the "Sign in" link, stashes both for the post-register success handler, and includes both in the `dataLayer.push({event: 'register_completed', source, returnTo})` that the audit cycle has been spec'ing since the 4/22 baseline.

**Fix (3 min, additive on top of the `?returnTo=` fix):**

```tsx
// register/page.tsx, in the same searchParams block:
const source = searchParams.get('source');

// After successful register:
if (typeof window !== 'undefined') {
  (window as { dataLayer?: Record<string, unknown>[] }).dataLayer ??= [];
  (window as { dataLayer: Record<string, unknown>[] }).dataLayer.push({
    event: 'register_completed',
    source: source || 'direct',
    return_to: returnTo || 'dashboard',
  });
}
```

**Impact:** First end-to-end attributable registration event in platform history. Composes with the homepage `?source=hero|final-cta` (5/11 P1 #3), the cross-site `/compare` source-attribution (5/5 P0 #2), and the still-unshipped `NewsletterSignup.tsx:32` `dataLayer.push`. **The first time a register conversion will be traceable to its origin surface.**

#### P0 (NEW today) — **The register form has three password-related fields where modern signup UX uses one.** Lines 80–108 render `password`, `confirmPassword`, with `confirmPassword` triggering a client-side mismatch check at line 22–25. Industry-standard pattern is a single password field with show/hide toggle and a strength meter (zxcvbn).

The `confirmPassword` field is the single most-skipped friction point on consumer signups — it doubles the typing volume, requires the user to remember the password they just typed (or paste, which password managers handle differently for the second field), and provides marginal correctness value (the user discovers password mismatch at next login anyway, and password-reset is one click away).

**Fix (15 min, additive after the `?returnTo=` and `?source=` fixes):** Remove `confirmPassword` state, remove the second password input, remove the mismatch check at lines 22–25. Optionally add a show/hide toggle to the remaining password field (~10 min more). The 8-char min check at line 27–30 stays.

**Impact:** Removes one full input field from the signup form. On password fields specifically, the literature consistently shows ~3–8% conversion lift from removing the confirm field. The exact magnitude is platform-dependent (cohort, mobile share, browser autofill share); the directional outcome is well-established. Single biggest signup-friction win available on the form today.
