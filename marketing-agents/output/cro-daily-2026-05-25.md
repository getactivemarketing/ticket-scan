### New findings today (in addition to the 17 carry-forwards from prior audits)

| # | Priority | Finding | Effort |
|---|---|---|---|
| **R-NEW-1** | **P0** | **No `autoComplete` attribute on any of the 3 inputs** (`:69–77`, `:84–92`, `:99–107`). Browsers cannot autofill the email field, the password manager cannot recognize the password fields as a new-credential pair, and 1Password / Bitwarden / Apple Passwords / Chrome's built-in PM all degrade silently to "no offer". **Mobile users especially feel this** — they have to swap to the password-manager app, copy, swap back, paste. **Fix:** `autoComplete="email"` on the email input (`:71`), `autoComplete="new-password"` on the password input (`:86`), `autoComplete="new-password"` on the confirm-password input (`:101`). The "new-password" value specifically tells password managers to prompt to *generate and save* a strong password — directly relevant for a "create account" flow. **3 single-attribute additions.** | 1 min |
| **R-NEW-2** | **P0** | **No password reveal/visibility toggle.** Both password fields are `type="password"`, which is correct for default state but defeats the user's ability to verify what they typed before submitting. **The mismatch check at `:22–25` fires only after submit** — a user who fat-fingers the confirmation gets the error, has to clear and retype *both* fields (since browsers don't expose the masked content), and friction compounds. Industry benchmark: an "eye" toggle next to each field reduces form abandonment by 6–9% on mobile (per Baymard Institute mobile-UX research). **Fix:** Add a small eye-icon button absolute-positioned over each password field; toggles `type` between `password` and `text` on click. Standard React pattern; ~15 lines. | 10 min |
| **R-NEW-3** | **P1** | **`"Password must be at least 8 characters"` is rendered only on submit-blocked, not inline as a hint.** A user reads the field label "Password", types 6 chars, clicks submit, gets the error, has to scroll up, fix, retry. **Fix:** Render `<p className="text-xs text-gray-500 mt-1">At least 8 characters</p>` immediately below the password input. The hint becomes a satisfied checklist when the user types char 8 (`text-green-600` with a checkmark icon, optional polish). Removes the round-trip cost on the most common error. | 5 min |
| **R-NEW-4** | **P1** | **Error message rendering at `:59–63` is in a single shared `<div>` above the form, not inline beside the field that errored.** The current 2 error sources are: "Passwords do not match" (field-level, belongs under `confirmPassword`) and "Password must be at least 8 characters" (field-level, belongs under `password`). A backend error like "Email already registered" *also* lands in the same shared box. **Fix:** Split into `emailError`, `passwordError`, `confirmPasswordError`, `formError` (for non-field errors). Render the first 3 inline under their respective fields with `role="alert"`; render `formError` in the shared red box at the top. Standard accessibility + UX pattern. | 15 min |
| **R-NEW-5** | **P1** | **No "Why create an account?" benefit copy on the page.** The form sits in a 480px card on a gray background with the heading "Create your account" + 1-line subhead "Start tracking ticket prices today". A cold visitor who landed here from the homepage CTA has zero reinforcement of *why* they're committing email + password. **Fix:** Add a 3-bullet list below the heading and above the form: *"✓ Track unlimited events"* / *"✓ Get price-drop alerts via email"* / *"✓ Compare prices across 3 ticket sites"*. Anchors the form completion to concrete benefits. | 5 min |
| **R-NEW-6** | **P2** | **No "Sign up with Google" / social SSO.** The single largest single-click reduction in registration friction is OAuth providers (Google, Apple, GitHub). Implementation cost is non-trivial (~half a day backend OAuth + ~half a day frontend + Google Cloud project setup), so this is the only P2 in today's set — but the leverage is large and growing as the platform tries to acquire users at the cold edges. **Defer until the P0/P1 fixes above ship.** | 1 day (deferable) |

### Register form — what's working

- **Field labels are explicit and aria-correct.** Each input has a real `<label htmlFor>` pair (lines 66, 81, 96). This is a stronger baseline than the newsletter form (which has no `<label>` at all — F3 yesterday).
- **8-char password minimum is reasonable.** Not overly strict, not dangerously lax. The newer NIST 800-63B guidance allows 8 as a floor when combined with deny-list checks (which the backend should but doesn't yet — separate finding for backend rotation, not today).
- **Loading state on the submit button (`:115`) — "Creating account..."** is the right verbose loading copy. *This is the pattern F4 yesterday asked the newsletter footer variant to adopt.* The newsletter component should match this pattern, not the inverse.
- **`router.push('/dashboard')` post-register at `:36`** is the correct success destination — drops the user immediately into the search surface (which is itself friction-laden per Day 26, but architecturally the right post-auth landing).
