## Wednesday Focus: Dashboard `/dashboard` re-audit

The Dashboard is the only page on the platform that *successfully* hands an anonymous visitor a working search interface. Unlike `/compare` (Day 43 hard-gated) and `/event/[id]` (Day 41 hard-gated) and `/watchlist` (gated, correctly, for an auth-only surface), the Dashboard accepts an anonymous search submit, returns real event results, and renders them through `EventCard`. **That is the platform's single working anonymous-conversion funnel** — and it is materially broken in 8 ways below, none of which require backend work.

The sign-up banner at `:60–75` is the closest thing the platform has to an in-flow registration prompt for a user who has already demonstrated intent (typed something, hit Search). The banner is **stationary above the search form** — it appears for non-logged-in visitors regardless of whether they've searched yet. It is positioned for arrival, not for intent. This is the central friction pattern on today's surface.

## Form Rotation: Price alert setup re-spec (Day 38)

**This form does not exist on any surface.** The platform tells users (homepage, every blog post, drip emails, every venue/WC page footer copy) that they can "get alerts when prices drop." The architecture is complete: cron firing every 4 hours × 38 days × 108 watchlist rows = ~72,576 successful price-checks; price_alerts table is set up; nodemailer is wired; the price-recommendation algorithm checks `currentPrice <= targetPrice` (per CLAUDE.md). The only missing piece is **the UI that captures `target_price` from the user.**

Yesterday's audit (E2 on EventCard) specified an inline target-price modal that opens *from* the EventCard's track button. Today's rotation re-specs the same form but with placement alternatives — the dev team may prefer to ship the modal on a different surface than the EventCard.

### Three plausible placements (ranked by ship-velocity)

**Placement A: Inline panel below EventCard's track button (E2 from yesterday).** Smallest scope change. Spec carries forward exactly: 90-min single-component edit. **Best for: ship-velocity.** Only file touched: `EventCard.tsx`.

**Placement B: Inline-edit on `/watchlist` page.** Add an "Edit target" pencil icon next to the "Target: $X" line at `watchlist/page.tsx:221–225`. Allows users to *set* (not just view) the target on rows that already exist. Bonus: addresses the existing 108 NULL rows — users who tracked something before the alert form existed can retroactively add a target. **Best for: unblocking the 108 stranded rows.** Requires a new `PATCH /api/watchlist/:id` route in `index.js` (or extending the existing PUT semantics). Two files touched: `watchlist/page.tsx` + `index.js`.

**Placement C: Standalone "Price alert" toggle on the `/event/[id]` detail page.** Same modal pattern, mounted on the event detail surface where users see the full price chart and the buy recommendation. **Best for: discoverability** — the user is on the page that *shows* the price history they want alerted on. Blocked by `/event/[id]` hard-gate (Day 41 carry); shipping this without fixing the gate creates a feature only logged-in users can ever see. **Defer until /event/[id] is unblocked.**

**Recommend: A + B as a single bundle.** A unblocks the forward path (new watchlist rows get a target on add); B unblocks the backward path (the 108 existing NULL rows can be backfilled by the user retroactively). C is the best long-term placement but is blocked on the `/event/[id]` hard-gate fix (Day 41 carry) and on the page being a client component (no metadata, no SEO).
