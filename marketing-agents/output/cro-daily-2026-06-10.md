## Page-Level Review — Dashboard / Search (`/dashboard`)

### ✅ What's right (keep it)
- **Not login-gated.** Anonymous visitors can search freely (`page.tsx` has no auth redirect). This is the correct value-first pattern — the exact opposite of the `/compare` wall flagged yesterday. Don't regress this.
- **Anonymous nudge is well-placed.** The non-logged-in banner ("Track prices and get alerts when they drop… Create a free account") with a "Sign Up Free" → `/register` CTA renders above results (`page.tsx:60-75`).
- **Value-first signup prompt on intent.** When an anonymous user clicks track, `EventCard` shows a "Track This Event → Sign Up Free / Maybe Later" overlay (`EventCard.tsx:80-104`) instead of a hard redirect. Good — it asks for the account *at the moment of intent*, after value is shown.

### 🟡 P1 — The core conversion action is an unlabeled `👁️` icon
**Evidence:** `EventCard.tsx:159-170`. The "track this event" button — the entry point to the entire signup funnel for anonymous users — renders as a small gray button whose only content is an eye emoji (`👁️`). Its meaning lives in a `title` tooltip (`EventCard.tsx:162`), which does **not** appear on touch devices.

Why it matters: "track prices / get alerts" is the product's differentiator, and on a search-results card it's represented by a wordless icon that most users won't recognize as "save / track." We're hiding the conversion lever.

**Recommendation (low effort):** Give the button a visible text label — `👁️ Track` (or "Track Price") — at least on `sm+`. Co-locate with the existing icon. This is a copy + className change in one component, applied everywhere EventCard renders (dashboard, and anywhere else it's used).

### 🟡 P1 — Above-the-fold value prop is generic; dashboard doesn't deliver the "compare" promise
**Evidence:** The page `h1` is just "Search Events" (`page.tsx:79`), and each result card shows a **single** price range from one source (`EventCard.tsx:142-147`, `$min – $max`). The cross-source comparison that the brand promises lives on `/compare` — which is login-gated (yesterday's P0).

So the logged-out journey is: land on dashboard → search → see single-source results + an outbound "Buy Tickets" link → the actual comparison value is behind a login wall. The dashboard's own copy never states the value prop (compare across Ticketmaster/SeatGeek/StubHub, track, get drop alerts).

**Recommendation:** Add a one-line value-prop subhead under the `h1` ("Compare prices across Ticketmaster, SeatGeek & more — then track for drop alerts"). This is cheap and on-voice. The deeper fix (surfacing multi-source price comparison in results, or un-gating `/compare`) is the standing cross-page item — not re-escalating here.

### 🟢 P2 — Outbound "Buy Tickets" visually outranks the retention action
`EventCard.tsx:150-171`: "Buy Tickets" is the full-width brand-colored primary (`flex-1`, `bg-brand`), while "Track" is a small gray secondary. We're giving the most visual weight to sending users *off-site* over capturing them into watchlist/alerts. Buy Tickets is likely monetization, so keep it — but elevate Track to co-equal weight (or pair the label fix above with a stronger style). Low priority.

### 🟢 P2 — `city` defaults to `'Orlando'`
`page.tsx:27` hardcodes `useState('Orlando')`. Fine for demoing a populated result set, but a Miami/NYC user must clear it first. Minor friction; consider a geolocation default or clearable chip. (Same note as the compare form yesterday — shared pattern.)

## Form Friction Check — Watchlist-add ("Track") flow (`EventCard.tsx:33-57`)

| Check | Status | Note |
|-------|--------|------|
| Field count | ✅ Zero-friction add | One click adds; no form to fill for the basic add. |
| Anonymous handling | ✅ Good | Shows value-first signup overlay, not a hard redirect (`EventCard.tsx:80-104`). |
| Button label | 🟡 Unlabeled | Icon-only `👁️`; tooltip-only meaning (see P1 above). |
| Loading / success feedback | ✅ Present | `adding` → `...`, `added` → green `✓`, button disables (`EventCard.tsx:159-170`). |
| Error feedback | ✅ Present | Inline red error on failure (`EventCard.tsx:172`). |
| **Target price capture** | 🔴 **Missing** | The add call sends only `eventId/eventName/eventDate/venue/city` — **no `target_price`** (`EventCard.tsx:43-49`). There is no field to set one. |

**🔴 Form gap — target price is never captured at the add step.**
The "track" action adds a watchlist row with no `target_price`. This is the **code-level source** of the standing, already-verified issue that price-drop alerts can't arm (watchlist items exist but `activeAlerts = 0` because nobody ever sets a target). The price-alert loop is severed at the very first step — the add UI gives no way to express "alert me when it hits $X."

This is a **known, verified standing issue**, so I'm not re-escalating it as new — but it's worth recording that the dashboard's primary add path is precisely where the target would need to be captured. **The minimal fix:** after a successful add (or in the track overlay for logged-in users), offer an optional "Alert me when it drops below $___" input that writes `target_price`. That single addition is what would let the existing alert cron actually fire.
