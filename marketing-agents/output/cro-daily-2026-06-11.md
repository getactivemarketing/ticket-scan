## Page-Level Review — Event detail (`/event/[id]`)

This is the product's **proof page** — the one screen that actually shows the value prop working: a price-history chart (`PriceChart`), a buy/wait/hold call (`BuyRecommendation`), a price-trend indicator, estimated section/tier pricing, and a multi-source price-check table. If a skeptical visitor is going to "get it," it happens here. Two structural problems keep almost nobody from seeing it.

### 🔴 P0 (NEW, code-verified) — The proof page is *orphaned from search*
**Evidence:** The only inbound link to `/event/[id]` anywhere in the app is `app/watchlist/page.tsx:237`. `EventCard` (the search-results card on `/dashboard`) has **no link to the event detail page at all** — confirmed by grep across `app/` + `components/`. It's not in `sitemap.ts` either.

Why it matters: the journey we *want* is search → see a result → open it → see the chart/recommendation → sign up to track. But search results dead-end at an outbound "Buy Tickets" link; there is no "View price history" affordance. So the single most persuasive page in the product is reachable only **after** a user has already registered and added something to their watchlist. We're showing the proof only to people who already converted.

**Recommendation (P0, medium effort):** Add a "View price history →" link on `EventCard` pointing to `/event/${eventId}`. Pair with the fix below so anonymous users can actually land on it. This connects the funnel's value-demonstration step that currently doesn't exist.

### 🔴 P0 (NEW, code-verified) — Hard login-gate with no value shown
**Evidence:** `page.tsx:108-112` — `if (!authLoading && !user) { router.push('/login'); return null; }`. Anonymous visitors are bounced to `/login` before a single pixel of the chart/recommendation renders. Same value-wall pattern already flagged on `/compare` (standing P0), now confirmed on the proof page too.

Mitigating context (why this is P0 *behind* un-orphaning, not ahead of it): today the only entry point is `/watchlist`, which is itself authed — so in practice no anonymous user reaches this redirect yet. But the moment we add the `EventCard → /event/[id]` link above, this gate becomes the thing that kills the new funnel step. **Fix both together, or the link just feeds the wall.**

**Recommendation:** Render a **preview** for anonymous users — show the chart and the buy/wait recommendation, then gate only the *action* ("Sign up free to track this event & get drop alerts"), mirroring the value-first overlay `EventCard` already uses (`EventCard.tsx:80-104`). At minimum, redirect to `/register` (not `/login`) with return context — a cold visitor has no account, so `/login` is the wrong default door.

### 🟡 P1 — `router.push` is called during render (React anti-pattern + flash)
**Evidence:** `page.tsx:109-112` calls `router.push('/login')` inline in the component body, not inside an effect. Navigating during render risks React's "Cannot update a component while rendering a different component" warning and can produce a content flash. **Fix:** move the redirect into a `useEffect`. Low effort; do it as part of the gate rework above.

### 🟢 P2 — Orientation assumes you came from the watchlist
`page.tsx:188-196`: the only nav on the page is a "← Back to Watchlist" link. If we start linking here from search (P0 above), a user arriving from `/dashboard` is told to go "back" somewhere they were never. Make the back-link context-aware, or use a neutral "← Back to results."

### ✅ What's right (keep it)
- **Honest data framing.** Tier pricing is labeled "Inferred… Not live per-section data" (`page.tsx:252-254`) and fees are disclosed ("Prices include estimated platform fees," `page.tsx:267-269`). On-brand consumer-advocate transparency — keep it.
- **Graceful empty state.** `priceHistory.length === 0` shows a "Price tracking just started… we check every 4 hours" card (`page.tsx:338-353`) instead of a blank screen. Good.
- **Parallel data fetch.** History/trend/recommendation load via `Promise.all` (`page.tsx:120-124`) — fast, single spinner.

## Form Friction Check — User registration (`/register`)

| Check | Status | Note |
|-------|--------|------|
| Field count | 🟡 3 fields | email, password, **confirm password** |
| Labels | ✅ Clear | Proper `<label htmlFor>` on all three (`:66, :81, :96`) |
| Email keyboard | ✅ | `type="email"` triggers email keyboard on mobile (`:71`) |
| **Autofill / password-manager** | 🔴 **Missing** | No `autoComplete` attributes on any field (`:69-107`) |
| Password rule visibility | 🟡 After-the-fact | "min 8 chars" only appears as an *error* post-submit (`:27-30`); never stated up front |
| Submit copy | ✅ Action-oriented | "Create account" / "Creating account…" loading state (`:115`) |
| Error feedback | ✅ Present | Inline red block (`:59-63`) |
| Newsletter opt-in | 🔴 Absent | No subscribe checkbox — ties to standing "/register opt-in still TODO" |

**🔴 Form fix #1 — add `autoComplete` attributes.** Missing autocomplete is the highest-impact friction here: mobile autofill and password managers won't reliably offer to fill or *save* the credential, hurting both completion and return-login. Add `autoComplete="email"` to email, `autoComplete="new-password"` to both password fields. One-line-per-input change.

**🟡 Form fix #2 — surface the password rule up front.** Show "At least 8 characters" as helper text under the password field instead of only failing on submit. Prevents the submit→error→retry loop.

**🟡 Consideration — drop "Confirm password" for a show/hide toggle.** Confirm-password is legacy friction; a single password field with a visibility toggle is the modern lower-abandonment pattern. (Lower priority than autocomplete — flag, don't mandate.)

## Bottom line
Today's review surfaced a real, previously-unrecorded structural gap: TicketScan's most persuasive page — the live price chart + buy/wait recommendation — is **orphaned from search and login-walled**, so it's only ever seen by users who already converted. The fix is a pair: link search results into it, and let anonymous visitors preview it before the ask. On the form side, the register page is clean but is missing `autoComplete`, which quietly suppresses autofill and password-manager saves. None of these need analytics to justify — they're plain funnel-topology fixes. Consistent with the standing read: the bottleneck is shipping, not analysis.
