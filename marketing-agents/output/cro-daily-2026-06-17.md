## Page Review — Dashboard / Search (`/dashboard`)

Read against source today (`dashboard/page.tsx`). Unlike `/compare` and `/event/[id]`, the dashboard is **NOT login-gated** — anonymous users can search and see results (`useAuth` is read but never redirects). That's good. The leaks here are about *value clarity*, not access.

**P1 — No value proposition on the page.** The only heading is `<h1>Search Events</h1>` (line 79) and the empty state says "Find your next event / Search for concerts, sports, theater, and more" (lines 182-183). Nowhere does the dashboard state what makes TicketScan different — **comparing prices across Ticketmaster, SeatGeek, and StubHub.** A first-time visitor landing here sees a generic event-search box indistinguishable from Ticketmaster itself. The core differentiator (the "scan/compare" promise in the brand) is invisible at the exact moment of intent.
→ **Recommendation (small copy + layout, ship task):** Add a one-line subhead under the H1 or in the empty state: *"We compare prices across Ticketmaster, SeatGeek & StubHub so you don't overpay."* Pure copy add; no new components. Hand to Content (Agent 1) for wording, dev to place.

**P2 — Zero social proof anywhere on the dashboard.** No user count, no "X events tracked," no sample savings, no testimonial. We have real, citable numbers (121 users, 149 watchlist items tracked) that could seed light social proof without fabrication. The empty pre-search state (lines 178-209) is prime real estate currently spent only on three blog links.
→ **Recommendation:** In the `!searched` empty state, add a small trust line using a real figure (e.g. "Tracking prices on 149 events for 121 members"). Must be sourced from live `/api/admin/stats`, not hardcoded — or omit rather than invent. Low effort, additive.

**P3 — Empty first paint = no demonstrated value.** On load (`!searched`) the user sees an empty form + a "Find your next event" card + blog tips. The product never *shows* a price comparison until the user manually searches. Consider pre-loading a small set of trending/popular events (the search API already returns events for the default city) so results render on first paint and the value is shown, not described. Medium effort (one default fetch on mount); note for backlog, not urgent.

**Minor — Hardcoded `city = 'Orlando'` default (line 27).** Same note as `/compare`: fine as a demo seed, but a non-Orlando visitor must clear it. Low priority.
