## Page Review — Event detail page (`/event/[id]`)

Re-verified against source today. This is the platform's **proof page** — price-history chart, buy/wait/hold recommendation, per-section tier estimates, recent-price table. It is the single best asset for converting an undecided visitor, and it is doing none of that work because of two standing access/discovery defects (both confirmed still present, not new):

**P0 (standing) — Login-gated to anonymous visitors.** `page.tsx:109-112` hard-redirects any logged-out visitor to `/login` before any content paints. The chart and recommendation — the exact "we'll save you money" proof — are invisible to non-members. This is a shipping task (anon read-only preview), not an analysis task; specced for 6+ weeks.

**P0 (standing) — Orphaned.** Re-grep today confirms the **only** inbound link to `/event/[id]` anywhere in the app is `watchlist/page.tsx:237`. `EventCard` (the search-result card on `/dashboard`) does **not** link to it — its two actions are "Buy Tickets" (outbound to the ticket site) and a watchlist eye-button. So the proof page is reachable only *after* a user has logged in AND added the event to a watchlist — i.e. only by people already converted. The asset that should *drive* conversion sits entirely downstream of it.
→ **Fix as a pair (unchanged recommendation):** (1) make the event title / a "View price history" affordance on `EventCard` link to `/event/[id]`; (2) allow an anon read-only preview of the chart + recommendation with a signup gate on the *interactive* bits. Both are ship tasks.

**P2 — "Back to Watchlist" is the only navigation.** `page.tsx:188-196` — the sole link out goes to `/watchlist`. An anon visitor (once un-gated) would have no watchlist and no natural next step. When the page is opened up, the back-link should be context-aware (back to search results) and the page should carry a primary CTA ("Track this event / set a price alert").

**Positive:** the page already handles its empty/loading/error states well, labels tier estimates honestly as inferred (lines 252-254), and discloses that prices include estimated fees (line 268). The content quality is fine — the problem is purely **who can see it and how they reach it.**

## Form Review — Price-alert / target-price setup (rotation item)

This is the highest-value finding of the day and it directly explains the 149→0 alerts anomaly. Traced end to end in source:

- **The API supports target prices.** `api.addToWatchlist()` accepts an optional `targetPrice` param (`lib/api.ts:169`). The backend plumbing exists.
- **The marketing copy promises it everywhere.** "Add it to your watchlist and **set a target price**. We email you the moment any platform drops to your target." — appears in `contact/page.tsx:68`, `faq/page.tsx:47`, `how-it-works/page.tsx:50`, `dashboard/layout.tsx:49`, `world-cup-2026/page.tsx:180`, plus testimonial copy on the homepage.
- **But there is no input control to set one — anywhere in the UI.** The only add-to-watchlist path is `EventCard`'s eye-button, which calls `addToWatchlist({ eventId, eventName, eventDate, venue, city })` with **no `targetPrice`** (`EventCard.tsx:43-49`). The watchlist page only *displays* a target if one exists (`watchlist/page.tsx:221-223`) and offers no field to set or edit it. The event detail page shows `targetPrice` inside the BuyRecommendation stats but provides no way to enter it. There is no modal, no inline field, no alert-setup form.

**Consequence:** every one of the 149 watchlist items is added with `target_price = null`, so the price-alert loop has nothing to compare against → `activeAlerts` is structurally pinned at 0 and can never arm. This is a **copy-vs-product gap** (we promise a feature that has no entry point) and a **missing form** at the same time.

→ **Recommendation (single small ship task, highest CRO leverage available right now):** add a target-price input to the add-to-watchlist flow. Minimum viable: a small number field in `EventCard`'s sign-up/track overlay (and an editable target on each `watchlist` row), passing `targetPrice` through the already-existing API param. Field spec: numeric, `inputMode="decimal"`, `$` prefix, optional, placeholder "Alert me below $___", action copy "Set alert." No backend change required. This converts a dead feature into the platform's core retention hook and is the only change that can move `activeAlerts` off zero.
