## Page Review — Venue page template (`/venues/[slug]`)

> Note on "top traffic venue": without analytics I cannot rank venues by real traffic, so this reviews the **shared template** (one file renders all 24). Findings apply to every venue — MSG (`/venues/msg`), SoFi, Chase Center, etc. Where traffic ranking would matter I flag it.

The template is **SEO-solid** (clean JSON-LD `@graph` with Place + ItemList + BreadcrumbList, null-safe offers, honest "Price TBA" / "* Prices vary" disclosures). The conversion path is where it leaks. Findings, in priority order:

**P1 — Every conversion action is a hard `/register` wall with zero proof shown first.** The per-event "Track Price" button (`page.tsx:260-265`), the sidebar "Start Free" CTA (`330-335`), and the empty-state link (`274-279`) all point to `/register`. A visitor who searched "MSG tickets," landed here, and sees "From $X" is asked to *create an account* before seeing a single price chart, trend, or buy/wait recommendation — i.e. before any of the value we promise. This is the same pattern that kneecaps `/event/[id]` (login-gated + orphaned, standing P0): the proof page exists but no venue visitor can reach it.
→ **Fix (pairs with the standing `/event/[id]` un-gate):** make the event row (title or a "View price history →" affordance) link to `/event/[id]` instead of, or alongside, the register wall. Show proof, *then* ask for signup. Ship task.

**P2 — No low-friction conversion offer on a high-intent page.** Venue pages are bottom-of-funnel (someone searching a specific venue has buying intent), yet the only asks are the hard register CTA and the global footer newsletter form. There is no venue-contextual soft capture — e.g. "Get price-drop alerts for events at {venue.name}." A one-field email capture converts far better than an account wall and feeds the (badly underweight) 3-subscriber list.
→ **Fix:** drop a `NewsletterSignup` (inline variant) with `source="venue-{slug}"` into the sidebar or below the events list. Low-effort, directly addresses the 122→3 registration↔newsletter gap.

**P3 — No social proof / trust signal anywhere on the page.** No user count, no "prices tracked," no testimonial, no "compared across N sites." The hero shows capacity and home teams; the sidebar shows abstract seating multipliers ("~1.5x base," `312-313`) that mean little to a consumer. For a price-comparison product, the absence of any "we track X sites / saved users $Y" line on a high-intent page is a missed trust beat.
→ **Fix:** add one credibility line near the events list ("Comparing prices across Ticketmaster, SeatGeek & StubHub"). Copy-only; route to Content (Agent 1).

**Positive:** honest price handling (real "From $X" only when `minPrice` exists, else "Price TBA"), good empty state, fast static render (`generateStaticParams` + 1h revalidate), clean breadcrumb + internal links to `/tickets/{city}` and blog. Content quality is fine — the gap is purely *what we ask for and when*.

## Form Review — Footer newsletter signup (`NewsletterSignup` footer variant)

Traced in source (`components/NewsletterSignup.tsx:45-77`). This form is now on every page via `Footer.tsx:11` (the fix logged in the newsletter-conversion root-cause work) — good. Friction findings:

**Strengths (keep):** single field; `type="email"` (correct mobile keyboard + native validation); `required`; inline loading, success, and error states; non-blocking async submit. This is a lean, well-built form.

**Fix 1 (copy, P2) — weak button verb.** Footer button reads **"Subscribe"** (`line 69`) — generic and effort-framed. The card variant already uses the stronger benefit-framed **"Get Deals"** (`line 102`). Match it: "Get Deals" or "Alert Me." Action/benefit copy beats "Subscribe" on newsletter CTAs. → Content (Agent 1), one-word change.

**Fix 2 (a11y, P2) — no label on the email input.** The footer input has only a `placeholder` (`line 60`), no visible `<label>` and no `aria-label`. Screen-reader users hear nothing identifying the field, and placeholder text disappears on focus. Add `aria-label="Email address"`. → dev, one attribute.

**Fix 3 (consistency, P3) — ambiguous loading state.** Footer loading text is `"..."` (`line 69`) while card/inline variants say `"Subscribing..."`. `"..."` reads as a glitch. Use "Subscribing…" for parity. → dev, trivial.

**Copy-accuracy watch (not a form change):** footer subcopy promises "price drop alerts" (`line 50`), but price alerts are inert platform-wide (0 active, 0 ever triggered — see anomalies). The newsletter is a *deals email*, not the alert system, so this isn't false, but the closer the two get conflated in copy the more we promise something that doesn't fire yet. Flagging for awareness; revisit once the target-price input ships.
