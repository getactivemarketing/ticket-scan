## Page-Level Conversion Review — `/venues/msg`

### Findings and recommendations

1. **P1 — The primary CTA is visible, but it skips the comparison step.** Each upcoming event offers `Track Price` and routes directly to `/register`; the sidebar offers `Start Free`, also to `/register`. A high-intent visitor cannot compare prices before being asked to create an account, and the event context is lost because the link has no `eventId`, `source`, or `returnTo` query parameters.

   **Recommendation:** Add a contextual `Compare Prices` link for each event, and change registration links to `/register?source=venue-msg&returnTo=/venues/msg&intent=watchlist`. Preserve the event ID when the API exposes it. **Effort:** ~20 minutes.

2. **P1 — The page does not offer a visible email capture path.** The page has event CTAs, seating guidance, related links, and blog links, but no `NewsletterSignup`. This is consistent with the platform-wide total of zero new subscribers today.

   **Recommendation:** Add one inline newsletter block after the upcoming-events list (or the empty state), with copy: “Get MSG ticket drops and fee-watch tips — no spam, unsubscribe anytime.” Use `source="venue-msg"`. **Effort:** ~10 minutes.

3. **P2 — Empty-state CTA is generic and not useful for a venue-intent visitor.** When no future events are returned, the page says “Sign up to get notified when events are announced,” but registration does not actually configure an alert or preserve the venue intent.

   **Recommendation:** Replace with two explicit choices: `Search MSG tickets now` → `/dashboard?city=New York&keyword=Madison Square Garden`, and `Get MSG event alerts` → a preserved registration/alert flow. Do not promise notification behavior until target-price/event-alert wiring is functional. **Effort:** ~15 minutes plus alert-flow dependency.

## Form Friction Check — Newsletter Signup (footer variant)

### Observations

- One required field; `type="email"` is correct, but `autoComplete="email"` and `inputMode="email"` are missing.
- Button copy is **“Subscribe”**, weaker than the inline variant’s outcome-oriented **“Get Deals.”**
- Loading state is only **“...”**, which is ambiguous and provides poor feedback.
- Empty submission silently returns before showing an error. Browser `required` catches normal submits, but no accessible validation message is provided.
- Success/error text is rendered as a paragraph without an explicit live region; assistive technology may not announce the result.
- No dataLayer event is pushed after a successful subscription, so newsletter conversion cannot be measured.
- Error text is shown below the form, which is reasonable, but the email field is not associated with the error via `aria-describedby`.

### Recommended form spec

1. Add `autoComplete="email"`, `inputMode="email"`, and a stable error/status ID.
2. Change the footer CTA from `Subscribe` to **`Get Ticket Deals`**; change loading text to **`Joining...`**.
3. Add `role="status"` / `aria-live="polite"` to success and loading feedback, and `role="alert"` to errors.
4. Push `{ event: 'newsletter_subscribe', source }` only after the API returns `success: true`.
5. On API failure, keep the email value and show a retryable, specific message. **Effort:** ~15 minutes.
