## Form Friction Review — Newsletter Signup

### Findings

- The form has one required email field, uses `type="email"`, has a loading state, and is reasonably compact for mobile.
- Placeholder copy is understandable but variant-dependent (“Enter your email” / “Get deals”); there is no visible `<label>` associated with the input.
- Loading feedback in the footer is only `...`, which is vague and not announced to assistive technology.
- Success and error messages are plain paragraphs without `role="status"`, `role="alert"`, or `aria-live`.
- Empty submission relies on the browser’s required validation; malformed/server errors are shown below the form but not tied to the input.
- No `name`, `autoComplete="email"`, or analytics event is present. The code does not distinguish form viewed, submit started, success, duplicate, or error.
- No newsletter popup implementation was found in the reviewed frontend sources; popup conversion is therefore N/A, not zero.

### Recommended form spec — P1

```text
Label: Email address
Supporting copy: Ticket deals and price drops. No ticket-broker nonsense.
Field: type=email, name=email, autoComplete=email, inputMode=email
Button: Get ticket deals
Loading: Joining…
Success: You’re on the list. We’ll send the useful deals, not inbox confetti.
Error: Enter a valid email address, or try again in a moment.
```

Add an associated label (visually hidden is acceptable), `aria-describedby` for supporting/error text, `role="status"` for loading/success, `role="alert"` for errors, and a disabled state that preserves readable button copy. Track `newsletter_form_viewed`, `newsletter_submit_started`, `newsletter_subscribed`, `newsletter_duplicate`, and `newsletter_error` without sending the raw email address.
