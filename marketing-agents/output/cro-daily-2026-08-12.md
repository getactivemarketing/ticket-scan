## Page-Level Conversion Review — `/dashboard`

### What works

- Guest users can reach the search interface without an account gate.
- The primary CTA, “Search Events,” is visible above the fold with four labeled controls.
- Search fields use appropriate text/date inputs, and date constraints prevent selecting dates before today.
- Guests get a clear account prompt: “Track prices and get alerts when they drop!”
- Results show date, venue, city, price range, and two next actions: buy or track.
- The responsive grid collapses to one column on small screens; a real-device Lighthouse/tap test remains outstanding. Live `/dashboard` HTML confirms GTM presence, but not Core Web Vitals.

### Recommendations

1. **P0 — Restore the product promise:** Repair the price-tracking cron and alert endpoint, then surface a small freshness/status cue near results (for example, “Prices checked today” or “Last checked …”). Do not imply current alerts while the data is stale.
2. **P1 — Make the above-fold value proposition specific:** Replace “Search Events” with copy such as “Find the lowest all-in price before you buy,” and add “Compare Ticketmaster and SeatGeek, then track drops for free.” This explains the consumer payoff before the first search.
3. **P1 — Give the watchlist action a stronger conversion path:** Change the icon-only guest action to a labeled “Track price” button on mobile and preserve the searched event in the signup URL/state, so registration returns users to the event they intended to save. Keep “Buy Tickets” as a secondary action until the tracking value has been understood.

## Form Friction Check — User Registration

### Current state

- Three fields: email, password, and confirm password. This is acceptable friction for an alert product.
- Email uses `type="email"`, required validation, and a mobile-friendly keyboard.
- Password fields use `type="password"`, but the form does not disclose the minimum eight-character requirement before submission.
- The form validates mismatch and minimum length, but displays both as generic text without field-level association or `aria-live` status.
- Submit feedback is present (“Creating account…”), but the destination is always `/dashboard`; the original searched event/context is not preserved.
- There is no visible privacy/alert expectation copy, password visibility toggle, or recovery path from the registration surface.

### Improvement specification

- **P1:** Add “At least 8 characters” beneath the password field and `autocomplete="new-password"` to both password inputs; add `autocomplete="email"` to email.
- **P1:** Use a field-associated, `aria-live="polite"` error region with actionable copy: “Use at least 8 characters” and “Passwords do not match.”
- **P1:** Preserve `returnTo`, event ID, and search parameters through registration; redirect back to the intended result or event after success.
- **P2:** Add a short expectation line: “Free price-drop alerts. No ticket purchase required here.”
- **P2:** Add a show/hide password control, especially for mobile users, without adding another required field.
- **P1:** Instrument `signup_view`, `signup_start`, `signup_submit`, `signup_error`, and `signup_complete` with source and return context; do not send email addresses to analytics.
