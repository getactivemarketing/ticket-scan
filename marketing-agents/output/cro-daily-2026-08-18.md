### Page-Level Conversion Review — `/compare`

**What works**

- Primary CTA is visible above the fold: **Compare Prices**.
- The value proposition is understandable quickly: “Find the best deals across multiple ticket sites.”
- The form uses visible labels, a responsive 1/2/4-column layout, native date inputs, and a clear loading state (`Searching...`).
- Production smoke check returned **HTTP 200 in ~0.24s server response time** and included the shared GTM container. This is not a Core Web Vitals measurement.

**Recommendations**

1. **P0 — Let visitors run a limited comparison before registration.** Preserve the query and selected event through any later signup modal; gate only save/watchlist/alert actions. This tests the product’s strongest promise before asking for credentials.
2. **P1 — Add decision-support proof directly below the form.** Show the sources currently available, fee-display policy, matching rules, and “checked at” freshness. The page metadata claims StubHub coverage, while the client model currently renders Ticketmaster and SeatGeek only; reconcile that promise before using it as trust copy.
3. **P1 — Add an explicit next action after results.** Each matched event should offer `Track this event` or `Set a price ceiling`, with account creation preserving event context. Current result actions primarily send users off-site to buy.
4. **P1 — Add event instrumentation.** Emit `compare_viewed`, `compare_started`, `compare_completed`, `compare_empty`, `compare_error`, `signup_started`, and `signup_complete`, including route, query dimensions, auth state, result count, source, and API outcome. Never include email or other sensitive data.

**Mobile check:** The form stacks at small widths and uses 44px-class input/button padding. Validate the result cards and source-buy buttons at 320px/375px; runtime interaction and Core Web Vitals were not available from this audit.
