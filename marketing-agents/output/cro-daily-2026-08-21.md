### Page-Level Conversion Review — Friday Focus

**Focus page:** Madison Square Garden venue guide — `/venues/msg`.

**Why this page:** The popular-events API repeatedly returns Madison Square Garden events among the strongest venue demand signals. This is a demand proxy, not page-traffic data; page-level traffic must be added to analytics before claiming it is the highest-traffic venue.

1. **P0 — Make the value proposition and primary action explicit above the fold.** The hero currently says “Madison Square Garden Tickets” and shows location/capacity, but does not immediately say “Compare Ticketmaster, SeatGeek, and StubHub prices” or offer a primary action. Add a short consumer-advocate subhead and a visible `Compare MSG prices` / `Track MSG prices` CTA that anchors to the event list or registration flow.
2. **P1 — Reduce the event-card commitment gap.** Each event’s `Track Price` link sends visitors to `/register` before they see an event-specific comparison or target-price setup. Preserve the selected event in the registration URL/state and return users directly to that event’s watchlist/alert setup after signup. This makes the promised action feel continuous rather than restarting the funnel.
3. **P1 — Add trust and decision support next to the event list.** The page explains seating tiers, but does not show a current comparison sample, fee caveat, last-checked time, or proof point. Add a compact “what you’ll compare” strip: all-in price caveat, marketplaces checked, and last refresh timestamp. Avoid invented savings claims.

**Mobile/performance check from source:** CTA buttons use adequate padding, and the event layout stacks on small screens. The venue page performs a server-side API fetch with a one-hour revalidation window, but no real-user timing data is available; add Web Vitals reporting before labeling load speed healthy or problematic.

### Form Friction Check — User Registration

The registration form has three fields: email, password, and confirm password. Email uses `type="email"`, passwords use `type="password"`, and the submit button has a loading state. Strengths: labels are present, browser validation is enabled, and errors are rendered inline.

**Recommendation — P1:** Remove the separate confirm-password field or replace it with a show-password control plus a clear password requirement. The current form creates an avoidable extra interaction and can produce a late “passwords do not match” failure. If confirmation is retained, validate matching on blur and associate the error with the confirm field using `aria-describedby`. Change the CTA to outcome-oriented copy such as **“Create account & track prices”** so the next value is explicit.

**Instrumentation required:** `register_view`, `register_start`, `register_error` (with error category only), and `register_success`; never send email addresses or passwords to analytics.
