### Page-Level Conversion Review — Compare Page

**What works**

- The signed-in page has a clear headline: “Compare Ticket Prices,” with a direct benefit statement: “Find the best deals across multiple ticket sites.”
- The primary CTA, **Compare Prices**, is prominent and action-oriented.
- Inputs have persistent labels: City, Event / Artist / Team, From Date, and To Date. Date constraints prevent past-date searches and keep the end date after the start date.
- The form collapses from four columns to one column on smaller screens; controls use generous padding and should be tappable on mobile.
- Live smoke checks returned HTTP 200 for `/` and `/compare`. Response-size checks were 132,587 bytes and 34,320 bytes respectively; this is not a Core Web Vitals or real-user load measurement.

**Recommendations**

1. **P0 — Let visitors compare before requiring registration.** Render `/compare` for logged-out users, preserve the current search state, and gate only save/watchlist/alert actions. After results, use a contextual CTA such as **Track this event and get price alerts**. This lets the user see value before asking for credentials.
2. **P1 — Make the first search easier.** City defaults to Orlando while keyword is blank. Add a useful example or popular-search chips and consider making Event / Artist / Team the first field on mobile. Measure search-start → successful-results rate once events are instrumented.
3. **P1 — Explain the comparison output before the first query.** Add one short line near the form: **See Ticketmaster and SeatGeek side by side, including estimated fees where available.** The page currently explains the benefit but not what the result view contains or what “best” means.
4. **P2 — Add persistent result-state actions.** After results load, keep **Track this event** beside the winning comparison and use the same action copy across cards. This should address the current zero-target-price activation signal.

**Mobile check:** The grid becomes one column at the `sm` breakpoint and the CTA remains full-width within the form row. Verify 320px and 375px widths in a real device/browser, especially date inputs and result cards; no RUM data is available.

### Form Friction Check — User Registration

- **Fields:** Three fields: email, password, confirm password. Confirmation adds friction, but it supports the current client-side validation. Test removing it only after backend/password reset coverage is confirmed.
- **Semantics:** Visible labels and `type="email"`/`type="password"` are correct. Add `autoComplete="email"`, `autoComplete="new-password"`, and `inputMode="email"` to improve mobile completion and password-manager behavior.
- **Error handling:** Client validation distinguishes mismatched passwords and passwords under eight characters. Preserve entered email on server/network failure and provide a specific retry instruction; the generic “Registration failed” path is not diagnostic for users.
- **CTA:** “Create account” is clear but does not reinforce the immediate benefit. Test **Create free account & track prices** after the compare-page gate is changed; keep the shorter copy as the control.
- **Loading state:** “Creating account...” communicates progress and the button is disabled. Add `aria-live="polite"` to the error/status region and move focus to it after a failed submission.
- **Trust:** The page says “Start tracking ticket prices today,” but does not state that the account is free or what the user gets next. Add **Free account · save events · get onsale and price alerts** near the submit button, only while those promises are operationally reliable.
