### Page-Level Conversion Review — Compare Page

**What works**

- The heading and promise are clear: “Compare Ticket Prices” and “Find the best deals across multiple ticket sites.”
- The primary button is action-oriented: “Compare Prices.”
- The form has explicit labels for city, event/artist/team, from date, and to date; date constraints prevent selecting dates before today or before the start date.
- The page has useful result framing: events found, price comparisons, source-only results, all-in pricing, and estimated section breakdowns.
- Production route returned HTTP 200 in approximately 0.40s from the audit location. This is server response time, not a Core Web Vitals or mobile Lighthouse result.

**Recommendations**

1. **P0 — Remove the auth redirect from comparison.** Let visitors search and see comparisons without an account. Gate only save/watchlist/alerts, with a contextual CTA after results: “Save this event and get price-drop alerts.” This preserves intent and moves signup after demonstrated value.
2. **P0 — Instrument the comparison funnel.** Emit `compare_form_viewed`, `compare_search_started`, `compare_search_succeeded`, `compare_search_failed`, `compare_result_viewed`, and outbound marketplace clicks. Include query dimensions, result counts, and latency; never send raw email or secrets.
3. **P1 — Make the first search feel less blank.** Keep the default city, add an example query such as “Magic” or “Taylor Swift,” and consider a populated example/search suggestion so the page demonstrates the result experience before the visitor commits.
4. **P1 — Add freshness and trust language to results.** Show the last-checked timestamp only when current, distinguish live prices from estimates, and present an honest unavailable state while price history is stale.

**Mobile review:** The search fields stack responsively and use large controls. The submit row is right-aligned on desktop; test 320px/375px widths to ensure the CTA remains prominent and keyboard focus is visible. No real-device or Lighthouse measurement was available.

### Form Friction Review — Watchlist / Price Alert Setup

- **Current fields:** none. `EventCard` sends event ID, name, date, venue, and city, but no target price.
- **Primary friction:** “Add to watchlist” creates a passive saved item, while the user-facing copy promises active price alerts. There is no place to state a budget, no confirmation that an alert is configured, and no path to activation.
- **Unauthenticated path:** the card opens a sign-up prompt, but the link goes to generic `/register` and does not preserve the event context.
- **Error handling:** the card uses `role="alert"`, which is good, but the success state is only the button icon changing to a check; there is no visible explanation of what was saved or what happens next.
- **Recommended minimum flow:**
  - CTA: `Set a price alert`
  - After auth, show the event name and a single required field: `Alert me when tickets are $___ or less`
  - Input: numeric/currency keyboard, min 1, clear currency formatting, optional “Skip for now”
  - Submit: `Start price alert`
  - Success: `Alert set — we’ll email you when this event hits $X.`
  - Preserve `eventId` and a safe return path through registration.
- **Instrumentation:** `watchlist_prompt_viewed`, `register_started_from_event`, `watchlist_added`, `target_price_started`, `target_price_set`, `target_price_skipped`, and `watchlist_error`.
