### Page-Level Conversion Review — Friday Focus: Madison Square Garden

Focus page: `/venues/msg` (Madison Square Garden). It renders successfully
and has useful venue-specific content: capacity, team context, seating tiers,
upcoming events, resale links, and onsale context. The page’s event list puts a
ticket link and a registration link beside each event, which is a strong
high-intent layout in principle.

Prioritized recommendations:

1. **P0 — remove or rewrite stale “Track Price” CTAs.** The current event
   cards link “Track Price” to registration even when the promised downstream
   price feature is unavailable. Use “Save for Onsale Updates” or “Add to
   Watchlist” only if the post-registration behavior is actually delivered.
2. **P1 — make the primary action explicit.** Keep “Resale tickets” as the
   main action and label the secondary action around the currently supported
   benefit: “Get Onsale Updates.” Add one short line explaining that TicketScan
   links out to the seller; this reduces surprise at the affiliate click.
3. **P1 — strengthen venue-page proof without unsupported pricing claims.**
   Surface “Capacity: 20,789,” the Penn Station access advantage, seating
   sections, and the next onsale/presale date near the first event list. These
   are concrete reasons to trust the guide and are safer than generic savings
   language.

Mobile note: the page’s event actions are text links and should remain at least
44px tall with clear separation. Confirm this in a real-device pass before
shipping a CTA rewrite.

### Form Friction Check — Friday Rotation

The scheduled Friday form is the price-alert setup form, but no active,
separate setup form was found in the current frontend. The closest live
flows are registration and the watchlist action.

Registration currently has three fields: email, password, and confirm password.
That is acceptable for a password account, but the value proposition says
“Start tracking ticket prices today,” which should be replaced with a supported
onsale/watchlist benefit. Improve the form with:

- a password requirement hint before submission (minimum 8 characters);
- `autocomplete="email"`, `autocomplete="new-password"`, and matching
  `inputMode`/mobile keyboard behavior;
- inline, field-specific errors rather than only a form-level error block;
- a clear post-submit destination explaining the next step: search an event
  and save it for onsale updates.

The newsletter form is structurally low-friction: one required email field,
`type="email"`, and a loading state. Its copy should stay focused on onsale
and presale dates; do not add price-alert language.
