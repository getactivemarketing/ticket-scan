## Form Friction Review — Homepage Newsletter Signup

### Findings

- The card variant has one required email field, uses `type="email"`, and has a loading state (`Subscribing...`).
- The field has no associated visible or visually hidden `<label>`, no `name`, and no `autoComplete="email"`.
- Success and error messages are not exposed with `role="status"`, `role="alert"`, or an `aria-live` region, so assistive-technology users may not receive the result.
- The submit button copy is generic (`Subscribe`); the surrounding promise is specifically onsale dates, so the CTA can be more descriptive.
- Empty input returns without a custom message and relies on native browser validation. Server errors are rendered below the form but are not associated with the field.
- No newsletter form view, submit-start, success, duplicate, or error event is emitted. Popup conversion remains **N/A**; no popup implementation was found in the reviewed frontend sources.

### Recommended form spec — P1

```text
Heading: Get onsale dates and useful ticket tips
Supporting copy: Presales, onsale dates, venue guides, and practical buying advice. No inbox confetti.
Label: Email address
Field: type=email, name=email, autoComplete=email, inputMode=email
Button: Get onsale updates
Loading: Joining…
Success: You’re on the list. We’ll send the useful stuff, not inbox confetti.
Error: Enter a valid email address, or try again in a moment.
```

Add `aria-describedby` for supporting/error text, a live region for loading/success, an alert region for errors, and an explicit disabled state that preserves readable button copy. Track named events without sending the raw email address.
