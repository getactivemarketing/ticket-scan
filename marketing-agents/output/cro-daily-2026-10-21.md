### Page-Level Review — `/compare`

The deployed route returns HTTP 200, but the client redirects unauthenticated visitors to `/login` before they can see or use the comparison form. This is the largest conversion leak: a high-intent visitor encounters account creation before receiving any product value.

Recommendations:

1. **P0 — Remove the pre-use auth wall.** Let visitors run a listing search as guests; require an account only when they choose to save an event or access a personalized dashboard. Preserve the intended search parameters through the auth redirect.
2. **P1 — Make the first action more specific.** Keep the four-field form, but make City required, move Event / Artist / Team first, and use a primary label such as “Find matching listings.” The current “Compare Listings” is accurate but vague before a search has happened.
3. **P1 — Add a clear empty/error state.** Explain that results show current seller availability and direct users to try a broader event name, city, or date range. Include one secondary link to browse the dashboard or onsale calendar.

Additional risk: the handoff records the underlying price-comparison integrations as currently unreliable. Until the data source is repaired, the page should avoid promising price savings, “BEST” pricing, or any price-based recommendation. Keep copy centered on finding events, seller links, onsale dates, and venue context.

Mobile and performance: the form uses responsive one-column fields, 44px-ish controls, labels, and native date inputs. No automated mobile performance or real-user timing data is available, so load-speed status is unverified.

### Form Friction Review — Newsletter Signup

Reviewed `NewsletterSignup.tsx`, including footer, inline, and card variants.

- **Fields:** one email field; good friction profile.
- **Input semantics:** `type="email"` and `required` are present; mobile email keyboard should activate.
- **Loading/error state:** present; the button disables while submitting and an inline error is shown.
- **Success state:** replaces the form with the API response message.
- **Copy issue:** the footer says “Get Onsale Alerts,” which is useful but slightly ambiguous about frequency/value; the inline variant’s “Get Alerts” is generic.
- **Instrumentation issue:** no explicit newsletter conversion event is pushed after a successful response.
- **Popup:** no newsletter-popup implementation was found in the reviewed component inventory, so popup conversion cannot be assessed.

Form recommendation: use a concrete, status-safe CTA such as **“Get onsale dates”** or **“Send me presale dates”** and add a success event with `source` and variant metadata. Keep the one-field form and current validation.
