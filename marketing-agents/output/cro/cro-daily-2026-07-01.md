## Page-Level Review — Dashboard/Search (`/dashboard`)

Analyzed `web/src/app/dashboard/page.tsx` and `web/src/components/EventCard.tsx`.

### CTA Visibility Above the Fold

**For non-authenticated users:** A sign-up banner is rendered above the search form (lines 61–75) in a `bg-gradient-to-r from-brand to-navy-light` strip with a "Sign Up Free" button. This is good — conversion entry point is visible before any interaction.

**For authenticated users:** No CTA above the fold (correctly — they're already converted). The search form renders clean and full-width.

### Value Proposition Within 5 Seconds

The page header says "Search Events" — this is functional but generic. It describes _what to do_, not _why TicketScan is different_. A user who arrived from a Google search for "cheap concert tickets" or a venue page sees no competitive hook. There's no sub-headline explaining "We compare prices across Ticketmaster, SeatGeek & more so you don't overpay."

### Critical Friction Points

**1. No path from search results to price comparison.**

This is the core funnel break on the dashboard. After a search returns events, users have two actions per card:
- "Buy Tickets" → external link, exits the site entirely
- 👁️ track → adds to watchlist (no alert arm, requires auth)

There is **no "Compare Prices" CTA** that routes to `/compare`. The dashboard is the highest-traffic internal page but it generates zero usage of TicketScan's core differentiator. The compare page exists but is unreachable from search results and is login-gated when found.

**2. "Orlando" as the hardcoded default city (line 27).**

`const [city, setCity] = useState('Orlando');` — Orlando is the company's home market, but this is almost certainly wrong for 60–80% of organic traffic arriving from non-Florida venues/city pages. Users who land on the dashboard see "Orlando" pre-filled and must type over it before searching. For mobile users, this means triggering the keyboard to clear a value they didn't choose. Low-friction fix: empty default with a meaningful placeholder.

**3. No "most-searched" quick-pick or discovery scaffolding.**

The pre-search empty state (lines 179–210) shows a TicketScan logo, "Find your next event" tagline, and three static blog links. There are no quick-start options ("Popular cities: NYC · LA · Chicago" or "Trending events: Taylor Swift · FIFA World Cup"). A user who doesn't know what to search for has no prompt — they see an empty text box with "Orlando" and a choice of three old blog posts.

**4. No social proof anywhere on the dashboard.**

The pre-search state has no user count or activity signal. "137 people are tracking ticket prices right now" would add credibility and nudge conversion. Even during the logged-in empty state, no trust signals appear.

**5. Post-search results don't amplify the CTA.**

When `events.length > 0`, the results header is only `{events.length} events found` (line 167). This is a high-intent moment — the user has already engaged enough to search and found results. A simple hook under the result count would convert: _"See which source has the lowest price → Compare now"_ linking to `/compare`.

### Mobile Experience

- Search form fields stack vertically on mobile (correct — `grid-cols-1` at smallest breakpoint)
- "Search Events" submit button is full-row-adjacent (right-aligned at `flex justify-end`) — not full-width on mobile, which means it occupies half the row width. Should be full-width on mobile.
- EventCard tappable areas are adequately sized
- The sign-up banner is full-width and visible on mobile — good

## Dashboard Recommendations (Priority Order)

### 🔴 P0 — Add "Compare Prices" action to search results

Every search result showing `event.priceRanges` should have a "Compare" action alongside "Buy Tickets." Minimum viable version: a second CTA in the EventCard button row that routes to `/compare?keyword={event.name}&city={event.city}`:

```tsx
{/* In EventCard.tsx, inside the mt-4 flex gap-2 buttons block */}
<Link
  href={`/compare?keyword=${encodeURIComponent(event.name)}&city=${encodeURIComponent(event.city)}`}
  className="flex-1 text-center border border-brand text-brand hover:bg-brand/5 py-2 px-4 rounded-lg font-medium transition-colors text-sm"
>
  Compare Prices
</Link>
```

This closes the biggest funnel gap: search → compare → register. Without it, the only path to conversion from a dashboard search is the 👁️ watchlist button (which requires auth and has no alert value). With it, a logged-out user clicking "Compare Prices" hits `/compare`, hits the auth wall, and has strong motivation to register.

Note: `/compare` must be un-gated before this is valuable. The login-gate at `compare/page.tsx:87-90` is the companion P0 from prior reports.

### 🔴 P0 — Default city to empty (remove "Orlando" hardcode)

## Form Friction Check — User Registration (`/register`)

| Check | Status | Finding |
|-------|--------|---------|
| Field count | ⚠️ **3 fields** | Email + password + confirm password — one field too many |
| Input types | ✅ | `type="email"` triggers email keyboard on mobile |
| Password visibility toggle | 🔴 **Missing** | No "show password" option — confirm-password exists to compensate, but both are opaque |
| Submit button copy | ⚠️ **Generic** | "Create account" — does not reinforce the value prop |
| Loading state | ✅ | "Creating account..." feedback on submit |
| Error messages | ⚠️ **Inline but generic** | "Passwords do not match" is clear; "Registration failed" is not — needs API error specificity |
| Social proof | 🔴 **None** | No "Join X users" or feature list anywhere on the page |
| Newsletter opt-in | 🔴 **Missing** | Every registration is a missed newsletter capture opportunity |
| Value prop on form | ⚠️ **Weak** | Sub-heading says "Start tracking ticket prices today" — correct, but no feature bullets |
| Mobile experience | ✅ | Single-column, large tap targets, correctly sized inputs |

### Key Finding: Confirm-password adds friction with no UX return

The registration form has 3 fields (email, password, confirm password). The confirm-password field exists because there's no password visibility toggle. The UX trade-off is poor: two password fields on mobile is harder to complete than one field with a show/hide button. Industry standard has moved to email + password + show-toggle. Net result: registration form is one field too long.

### Fix Spec — 3 changes with high leverage

**1. Replace confirm-password with a show/hide toggle (reduces fields from 3 to 2):**
```tsx
const [showPassword, setShowPassword] = useState(false);
// ...
<div className="relative">
  <input type={showPassword ? 'text' : 'password'} ... />
  <button type="button" onClick={() => setShowPassword(!showPassword)}
    className="absolute right-3 top-1/2 -translate-y-1/2 text-gray-400 hover:text-gray-600 text-sm">
    {showPassword ? 'Hide' : 'Show'}
  </button>
</div>
```
Remove the confirmPassword state, the field, and the client-side mismatch check.

**2. Change submit button copy:**

Current: `Create account`
Proposed: `Start Tracking for Free`

Ties the action directly to the product value. One-line change at `register/page.tsx:115`.

**3. Add a newsletter opt-in checkbox:**
```tsx
{/* Add above the submit button */}
<div className="flex items-start gap-3">
  <input type="checkbox" id="newsletter" defaultChecked
    className="mt-1 h-4 w-4 text-brand rounded border-gray-300 focus:ring-brand" />
  <label htmlFor="newsletter" className="text-sm text-gray-600">
    Send me weekly price drop tips and ticket buying strategies
  </label>
</div>
```
Pass the value to the register API call and auto-subscribe on opt-in. This is the fastest path to newsletter growth — the 137 users who already registered didn't have this option.
