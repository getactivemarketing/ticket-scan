## Page-Level Conversion Review — `/compare`

### What is working

- The page has a clear H1: **“Compare Event Listings.”**
- The supporting explanation is understandable and status-safe at the top: it says users can find the same event across ticket sites and review seller details.
- The search form uses visible labels for city, event/artist/team, from date, and to date.
- Inputs have comfortable padding and the layout collapses from four columns to a single column on small screens.
- The submit button is specific: **“Compare Listings.”** Loading feedback changes it to **“Searching…”** and disables repeat submission.
- Results have a clear matched/all toggle and seller links open in a new tab.

### Recommendations

1. **P0 — Let visitors search before requiring registration.** Render the comparison form for anonymous users. Require an account only when the visitor chooses to save an event, and preserve the search query/event context through registration. This removes a hard login wall from the core acquisition path.

2. **P0 — Reframe comparison output around availability and seller verification until data health is restored.** Remove or suppress TicketScan-generated “BEST,” “Save $X,” fee-estimate, and section-price presentation unless each value is independently current and approved. Use status-safe labels such as **“Available on Ticketmaster”**, **“Available on SeatGeek”**, and **“Check current availability and the all-in total on the seller site.”** Do not replace these with buy-timing or alert language.

3. **P1 — Give the empty state a useful next action.** The matched view currently says “No matching events found” and points users to another tab. Add a clear secondary action such as **“Browse all events”** or **“Search upcoming events”**, plus a short note that sellers may list the same event differently. Keep it factual and avoid implying that a missing match represents a price opportunity.

4. **P1 — Add a compact trust cue near outbound seller CTAs.** For example: **“Ticket details, availability, fees, and delivery terms are confirmed on the seller site.”** This gives users a reason to continue without promising that TicketScan owns or continuously monitors seller data.

## Form Friction Review — Newsletter Popup Rotation

### Finding

There is no newsletter popup implementation in the reviewed frontend sources, so popup views, starts, abandonment, conversion, and dismissals are all **N/A**. Creating a popup is not the first recommendation while the current newsletter delivery/reporting path is not observable.

The fallback `NewsletterSignup` component has one required email field, the correct `type="email"`, loading/success/error state handling, and no unnecessary fields. It is missing several accessibility and measurement details:

- no visible or programmatically associated label;
- no `name="email"` or `autoComplete="email"`;
- success/error copy is not exposed through a live region;
- generic button labels (`Subscribe`, `Get Alerts`) do not explain the benefit;
- card/footer copy says “alerts,” which is too broad while only onsale/presale information and tips are safe to promote;
- no lifecycle events distinguish view, submit, success, duplicate, or error.

### Recommended form spec — P1

```text
Heading: Get onsale dates and useful ticket tips
Supporting copy: Presales, onsale dates, venue guides, and practical buying advice. No inbox confetti.
Label: Email address
Field: type=email, name=email, autoComplete=email, inputMode=email
Button: Get onsale updates
Loading: Joining…
Success: You’re on the list. We’ll send useful ticket updates, not inbox confetti.
Error: Enter a valid email address, or try again in a moment.
```

Add `aria-describedby` for supporting/error text, `aria-live="polite"` for loading/success, `role="alert"` for errors, and a disabled state that preserves readable loading copy. Emit non-PII events such as `newsletter_form_viewed`, `newsletter_submit_started`, `newsletter_subscribed`, `newsletter_duplicate`, and `newsletter_error`, with page path and placement only.
