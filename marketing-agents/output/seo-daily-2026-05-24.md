Source: `web/src/app/tickets/[slug]/page.tsx`. JSON-LD parses cleanly (2 blocks: layout Organization + page `@graph` with ItemList and BreadcrumbList). Per-event analysis of the 5 ListItem entries on `/tickets/orlando`:

| Field | Coverage | Google requirement |
|---|---|---|
| `name` | 5/5 | required |
| `startDate` | 5/5 (but date-only, no time) | required, datetime preferred |

| `location.address.addressLocality` | 5/5 | required (partial — city only) |

| `performer` | 0/5 | recommended for concerts |
| `address.streetAddress`/`postalCode`/`addressRegion`/`addressCountry` | 0/5 | recommended for venue address |

**Net rich-result eligibility:** Each Event item is **minimally compliant** (passes the required-field bar) but **missing most recommended fields**. Google's Event rich-result documentation states that pages without `image`, `offers`, and full venue address are eligible but unlikely to win the image-carousel or price-snippet treatments in SERP — both of which competitors (SeatGeek, Vivid Seats, Ticketmaster) routinely earn on city/category pages.

**Three observations from today's rotation:**

1. **Offers coverage is 20% (1/5).** Only the "Sunday Punk Brunch" event ships `AggregateOffer.lowPrice=15.5`. The other four events have no pricing in the JSON-LD because the upstream `/api/public/events?city=orlando` response apparently doesn't include `minPrice` for those four. Root cause is data-pipeline, not template: the `events` array passed into the page from `getEvents()` (line 89 of `tickets/[slug]/page.tsx`) is missing `minPrice`/`maxPrice` for most rows. This mirrors the `lowPrice` regression on WC stadium pages — both surface the same upstream gap: price-data is sparse on Ticketmaster-sourced events without a confirmed `priceRanges[0].min` field. Worth a content-data-touch flag to the Content/backend stream.

2. **No `endDate`, `eventStatus`, `eventAttendanceMode`, `image`, `description`, or `performer` on any of the 5.** All are Google-recommended for Event rich results. `eventStatus` defaults to `EventScheduled` and is trivial to add as a static field. `eventAttendanceMode` defaults to `OfflineEventAttendanceMode` and is similarly trivial. `image` would need to flow from the upstream Event object — currently the `Event` interface (lines 8-18 of `tickets/[slug]/page.tsx`) has no image field. `endDate` and `description` are data-source gaps. **Recommend adding the two trivial defaults (`eventStatus`, `eventAttendanceMode`) as static fields in the template, even without data-pipeline work — that's a 4-line code change that lifts rich-result eligibility on all 37 ticket pages.** Logging as a bundle candidate but not patching today (bundle frozen).

3. **`Place.address` is incomplete (city-only).** Every event ships only `addressLocality`. No `streetAddress`, `addressRegion` (state), `postalCode`, or `addressCountry`. The venue-level data exists in `web/src/data/venues.ts` for the 24 known venues — but the events come from the upstream API which returns just the venue name + city string. A template enhancement could lookup the venue against the local venues.ts data and enrich the address when there's a match (e.g., "Camping World Stadium" → match to `web/src/data/venues.ts` entry, populate `streetAddress`/`postalCode`/`addressRegion`/`addressCountry`). Higher-effort patch, deferred.

**Comparison to the 5/19 rotation (last time `/tickets/[slug]` was checked):** That report focused on the ItemList parent shape (correct then, correct now). It did not enumerate Event-child field coverage. So findings 1–3 above are net new from this rotation. They are quality-degradation, not regression — the fields were never present.

Schema syntax: clean. Rich-result eligibility: minimally compliant, significantly under-optimized vs. Google's recommended schema for Event/ItemList. **Highest-leverage fix is the 4-line static-default insertion (`eventStatus` + `eventAttendanceMode`) — would apply across all 37 `/tickets/[slug]` pages from a single template edit.**
