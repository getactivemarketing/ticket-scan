## Errors found

### NEW (high-severity, **retraction**) — WC `lowPrice` is a logic bug, not a deploy-divergence

**Today's methodology** (now codified): fetch live HTML first, then compare to `git show HEAD:<path>` and to the working-tree blob. Applied to `/world-cup-2026/[stadium]/page.tsx`:

| Source | What it contains | `lowPrice` it produces |
|---|---|---|
| **HEAD blob** (`git show HEAD:web/src/app/world-cup-2026/[stadium]/page.tsx`, 221 lines) | **No JSON-LD at all.** Plain page render only. No `@context`, no `schema.org`, no `extractLowestPrice()`. | N/A — produces no schema |
| **Working-tree blob** (285 lines, 64-line addition) | Adds OpenGraph/Twitter metadata + full `StadiumOrArena` + nested `SportsEvent` + `AggregateOffer` JSON-LD. Computes `lowPrice` via `extractLowestPrice()`. | $15000 for ATT, $10000 for Mercedes-Benz, $8000 for Lumen, $6000 for Levi's |
| **Live HTML** (cache-busted fetches at 10:05 UTC) | Matches working-tree shape exactly. JSON-LD present, all fields match WT. | $15000 / $10000 / $8000 / $6000 — **same as WT** |

**Why the WT produces $15000 (not the previously-claimed $150):**

```ts
// web/src/app/world-cup-2026/[stadium]/page.tsx, lines 55-61 (working tree)
const extractLowestPrice = (): number | undefined => {
  for (let i = venue.sections.length - 1; i >= 0; i--) {
    const match = venue.sections[i].priceRange.match(/\$(\d+)/);
    if (match) return parseInt(match[1], 10);
  }
  return undefined;
};
```

The loop iterates **backward** through `venue.sections` (from `length-1` to `0`) and returns the **first match**. Inspecting `web/src/data/worldcup.ts`, the **last entry** in each stadium's `sections` array is a Suite Level priced at $6,000–$15,000+:

- MetLife: last entry = `MetLife Suite Level` @ `$15000-$50000+` → returns `15000`
- ATT Stadium: last entry = Suite Level @ `$15000-…` → `15000`
- Mercedes-Benz: last entry = Suite Level @ `$10000-…` → `10000`
- Lumen Field: last entry = Suite Level @ `$8000-…` → `8000`
- Levi's Stadium: last entry = Suite Level @ `$6000-…` → `6000`

Verified live across four stadium URLs (ATT, Mercedes-Benz, Lumen, Levi's, MetLife) — all match.

**The bug:** the function computes the *last-section first-dollar-value* rather than the *minimum across all sections' first-dollar-values*. For Google Merchant / event-rich-result eligibility, `lowPrice` is supposed to be the lowest available ticket price; advertising $15,000 as the lowest WC group-stage ticket at MetLife is both wrong AND directly disqualifying for the rich result (Google's structured data guidelines require `lowPrice` ≤ `highPrice` and that the values be honest).

**Correct fix** (single line, isolated to the function):

```ts
const extractLowestPrice = (): number | undefined => {
  const prices = venue.sections
    .map(s => s.priceRange.match(/\$(\d+)/))
    .filter((m): m is RegExpMatchArray => m !== null)
    .map(m => parseInt(m[1], 10));
  return prices.length > 0 ? Math.min(...prices) : undefined;
};
```

Expected output after fix: MetLife `150`, ATT `60` (lowest GA category), Mercedes-Benz `80`, Lumen `80`, Levi's `60` — all in plausible group-stage cheapest-tier range.

**Day-counting reset:** the "Day 18 lowPrice regression" framing in yesterday's report (and Days 17, 16, … back to the 5/10 initial flag) was based on a misreading of which code produces which value. The bug has existed since the JSON-LD was first added to the working tree (`git log -- web/src/app/world-cup-2026/[stadium]/page.tsx` shows the file was committed once at initial restructure, with no JSON-LD; the JSON-LD addition is uncommitted in WT). The correct framing is: **the function has been buggy since the JSON-LD was first written, and the buggy values have been live since the JSON-LD first shipped**. No "regression" — original logic was wrong.

**Larger structural issue: SportsEvent is being used at the wrong granularity.** A SportsEvent should be a single match (e.g., "USA vs Mexico, June 14, 2026, MetLife"), with its own `startDate`, `homeTeam`/`awayTeam`/`competitor`, its own `offers`. The current schema models the *entire tournament-at-this-venue* as one SportsEvent with a 38-day startDate→endDate range. Google may still accept it, but it's not eligible for the per-match rich result (the one that surfaces "Tickets from $X for USA vs Mexico" in search). Per-match SportsEvent records would require structured per-match data in `worldcup.ts`, which would be a content-data lift. Routing as a Phase-2 ask to Content Agent.

**Net rich-result eligibility (after `lowPrice` fix):** **Pass minimum.** With the `extractLowestPrice()` fix and adding `highPrice` + `offerCount`, the page would be eligible for the AggregateOffer rich result. To unlock the per-match SportsEvent rich result, would need per-match data structures.

The page references `JSON.parse` (typical Next.js `__NEXT_DATA__` hydration pattern), suggesting all schema is client-rendered. Googlebot would only see this if JS execution succeeded during crawl, which is best-effort.

**Comparative reading:** TicketScan's SSR'd JSON-LD via Next.js static generation is **structurally ahead** of both these competitors on schema discoverability. Both StubHub and SeatGeek (5/26 spot-check) ship static JSON-LD; Vivid Seats blocks bots; Gametime relies on client-side rendering. So in the broader competitive set, TicketScan and the two larger competitors (StubHub, SeatGeek) form one cluster (static JSON-LD), and the smaller two (Vivid Seats, Gametime) form another (bot-blocked / client-rendered). This is a real, defensible structural advantage **for the parts of our schema that are correct.** Today's WC `lowPrice` bug means we're shipping a structurally-valid schema with a wrong value — the worst of both worlds (Google parses it, accepts the bad value, may either downrank or display the wrong figure).
