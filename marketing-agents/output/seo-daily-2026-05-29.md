## Technical fix applied

**File:** `web/src/app/tickets/[slug]/page.tsx`
**Change:** 8-line addition before `events`-derived logic. Renamed the raw API return to `rawEvents` and built a deduped `events` array filtering by `name|venue|date` key.

```ts
const rawEvents = await getEvents(slug, pageData.type);

// Deduplicate events by (name + venue + date) so recurring same-day showtimes
// collapse to one entry in both the rendered list and the ItemList JSON-LD.
// Google's structured-data guidance requires distinct ListItem entries, and
// the public events API can return multiple showtimes of the same event.
const seenEventKeys = new Set<string>();
const events = rawEvents.filter((event) => {
  const key = `${event.name}|${event.venue}|${event.date}`;
  if (seenEventKeys.has(key)) return false;
  seenEventKeys.add(key);
  return true;
});
```

All downstream consumers (UI rendering at line 248, schema construction at line 159, `numberOfItems` at line 200) now read the deduped `events`. No other call sites changed.

**TypeScript check:** `./node_modules/.bin/tsc --noEmit` → exit 0, no errors.

**Why fix in the page rather than at the API:** The dedup is a presentation concern (we want one entry per name+venue+date for city/category list pages). A different consumer of the API (e.g. an individual event page showing all showtimes) would legitimately want all the rows. Keeping the dedup at the page level preserves API generality.

The page-level fix handles ItemList correctness today, but if other consumers also want deduped events, doing it once at the API is cleaner long-term.

## Competitor insight

**Today's rotation:** Ticketmaster MSG venue page (per the 5/27 plan: "rotate back to a head-to-head … under `Event.subEvent`"). Fetched `https://www.ticketmaster.com/madison-square-garden-tickets-new-york/venue/483329` via desktop UA at 10:08 UTC. The site returned a 200 with full HTML (no UA block — unlike StubHub which 403'd today, and SeatGeek which returned empty `<script type="application/ld+json">` tags).

**Pattern:** Ticketmaster emits an **array of individual top-level Event/MusicEvent JSON-LD nodes**, one per upcoming event, NOT an ItemList wrapper. Each event has:

```
@type: MusicEvent  (or Event for non-music)
url: <ticketmaster deep link>
name, description, image (empty string in this sample), startDate (full ISO datetime), endDate
eventStatus: https://schema.org/EventScheduled
eventAttendanceMode: https://schema.org/OfflineEventAttendanceMode
location: {
  @type: Place
  name: "Madison Square Garden"
  sameAs: <ticketmaster venue URL>
  geo: { @type: GeoCoordinates, latitude: "40.749706", longitude: "-73.9916" }
  address: { streetAddress: "7th Ave & 32nd Street", addressLocality, addressRegion, postalCode, addressCountry }
}
offers: {
  @type: Offer  (NOT AggregateOffer)
  availability: http://schema.org/InStock
  description
  url
  validFrom: <ISO timestamp ticket sale started>
  availabilityStarts: <same>
}
```

Note `subEvent` is NOT used — Ticketmaster's pattern is one Event node per Event, no parent-child nesting. The `Event.subEvent` framing in the 5/27 plan presumed a different shape that competitive practice doesn't follow.

**Tactical takeaways for TicketScan:**

1. **Per-event Event nodes, not ItemList, are the higher-leverage schema pattern for venue pages.** TicketScan's `/venues/[slug]` page currently has NO Event schema (5/28 audit noted this gap; today's competitor evidence reinforces it). Re-flagging to the Content Agent backlog as **high priority** (was previously "high value, low effort"). Concretely: for each event the page renders, emit a top-level Event node with `name`, `startDate`, `url`, `location` (existing venue data), and `offers` with `lowPrice` from the existing minPrice. Constant string fields (`eventStatus`, `eventAttendanceMode`) are free.

2. **`Offer` (singular) vs `AggregateOffer`.** Ticketmaster uses `@type: Offer` per event — single price point per Offer node. TicketScan currently uses `@type: AggregateOffer` everywhere. Both are valid; `Offer` is appropriate when the page represents one ticket option (deep link to a specific event), `AggregateOffer` is for "many tickets across a venue or tournament." The /tickets/[slug] ItemList is correctly using bare `Event` with `AggregateOffer` (would represent "tickets to this event from $X to $Y" — still appropriate). The WC stadium pages are correctly using `AggregateOffer` (multi-section pricing). No change recommended.

3. **`offers.validFrom` and `availabilityStarts`.** Ticketmaster ships these per-offer. Both signal to Google that the offer is live and when ticket sale opened. We have presale/onsale data in the upstream API but it's not flowing through. Defer to Phase 2.

4. **`location.geo` and `streetAddress`.** Both consistently present on Ticketmaster's venue pages. TicketScan's `/venues/[slug]` schema lacks both. Already on backlog from 5/26 venue data-touch request. Bumping to high priority.

**Comparative reading update:** TicketScan ships static SSR'd JSON-LD via Next.js (same cluster as Ticketmaster). StubHub blocked the request today (403), SeatGeek returned empty JSON-LD shells (client-rendered). Among the 4 majors, TicketScan and Ticketmaster are the two with crawlable static JSON-LD — but Ticketmaster's per-Event-node coverage is meaningfully richer than ours. Closing the per-event-schema gap on `/venues/[slug]` would put us at parity with the deepest schema implementation in the competitive set.
